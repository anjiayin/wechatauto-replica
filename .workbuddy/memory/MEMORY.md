## 铁律 / 常踩的坑
- pytest 用 `/d/my_conda_envs/wechatauto/python.exe -m pytest`（只有这个环境装了 pytest 9.2.0 + 项目依赖，PATH 里的 python 没有）；必须 `--basetemp=D:/tmp/pt-新目录名`（本机 safe-delete 守卫会拦临时目录清理，复用旧目录会报一堆 tmp_path fixture 错）；全量约 9 分钟。
- UIA 实机测试只允许「文件传输助手」，**禁止向真实联系人/群发消息**。
- **托盘态想自动发送，只能模拟点击托盘图标让 Qt 自己 show()**（2026-11-15 19:05 实测 2.62s 成功）：①再启动 `Weixin.exe` **不是唤起**，实测新起 PID + 296x388 新窗口后自行退出、旧主窗仍在托盘（18:53）；②`SW_SHOW` 是第 5 轮已证伪的畸形态元凶。实现见 `wechatauto/tray_restore.py`：图标名称精确匹配 + **按矩形面积选 40x40 图标按钮**（溢出面板里有同名 37x22 文本标签）+ 溢出面板 UIA 子节点轮询等 2s（固定 sleep 0.6 会扑空）+ **单击 0.8s 无效补一次双击**（单击不总生效）+ V 形重试阈值 ≥1s 防误收起 + 保存/恢复鼠标并收起面板；绝不 `ShowWindow`/写内存/起新进程。唤起成功必须走 `guia._after_tray_restore()` 清 UIA/会话/输入框/句柄缓存；后台预热巡检仍不碰托盘窗口。pytest 由 `tests/conftest.py` autouse 隔离，绝不真的点桌面图标。
- **异步 202 + WS `send_result` 要保证「受理先于结果」**（2026-11-15 18:26 实测）：回复接口跑在 threadpool，广播走 `run_coroutine_threadsafe` 投递主循环；0 秒失败（托盘态 fail-closed）时 WS 结果比 202 更早到浏览器，被前端 `onSuccess` 的「已加入发送队列」覆盖成「只进队列、没反应」。后端 `ACK_LEAD_SEC=0.35`（`SendTask.enqueued_mono` + `_run` 用 `Event.wait` 等待）+ 前端 `sendSettledRef` 双重保险，别只留一边。另外**所有失败路径都必须广播 `send_result`**，`_ensure_gui()` 返回 None 只发 `status_change` 会让前端「发送中」永不结束。
- 微信只读探查用 `WeChatDB(workdir=r'D:\wechatauto_cache')`；真实微信库在 E 盘 `E:\xwechat_files\...`，`auto_detect_db_dir()` 返回的 `E:xwechat_files` 缺反斜杠，必须 `os.path.abspath()`。
- 时间口径一律交给 SQLite `datetime('now','localtime',...)`；Python 拼 `T` 分隔时间字符串会因 TEXT memcmp 误删整日数据。
- `voice_texts` / `ai_usage` / `voicecache` 不参与界面「立即清理」（`_PURGE_TABLES` 只有 analysis_logs + opportunities）。
- `kefu-system/data/` 已 gitignore（ASR 模型 229MB、语音/图片缓存）；`tools/silk_v3_decoder.exe` 已被 git 跟踪。

## 领域结论（已实测，别再推翻）
- **「回复时好时坏 / 界面卡死」先查窗口状态与热激活配额，别查会话名、网络、AI**（2026-11-14 23:39~23:51 实测）：①最小化窗口 `IsWindowVisible` 仍 True，但 `GetWindowRect` 是 `(-32000,-32000,-31840,-31972)` 即 160×28 伪矩形；被绑成 `main_hwnd` 后布局/输入框/侧栏全错（日志「校准=1108 vs 当前=280」），3 轮重试耗 60~80s。②`_hot_activate_accessibility` 曾把 gate 已为 1（什么都没写）也返回 True 并计入限流，日志只见 3 次真实 0→1 却报「已热激活 5 次」→ 300s 内强制 OCR 兜底；配额重置后立刻流畅，这就是「时好时坏」的时钟。③sender 每次发送两次 `bring_to_front` 翻转 Z 序 + rebind 清 `_uia` 触发预热巡检再打补丁，形成自激循环；补丁写太频会把 Qt 输入系统写挂（界面卡死）。现已修：guia 淘汰 IsIconic/伪矩形 + `_locate_main_window` 自动恢复最小化窗、ensure_visible 缓存校验「微信仍在前台」；uia_driver 三态只计真实写入 + 按 PID 去重 + 等待期间每 6s 重试；sender 置前统一交给 ensure_visible。排查入口 `kefu-system/wechatauto_logs/app_YYYYMMDD.log` 的「热激活」「重绑 hwnd=」「自动最小化遮挡窗口」。
- **回复「时好时坏」若只有引用失败、纯文本/@ 全正常，查引用路径而不是窗口/树**（2026-11-15 00:21~00:28 实测）：①微信 @ 消息原文是 `@昵称\u20055`（U+2005 四分之一 em 空格），`_quote_snippet` 的 `" ".join(text.split())` 把它折成 U+0020，而 UIA 消息行 Name 保留 U+2005 → 包含匹配恒 False；现用 `wechatauto/text_norm.py` 双向归一化。②`find_in_message_list` 向历史滚最多 12 次且**失败不复位** → 面板停在历史消息处（用户看到「滑块在动却不输入」），并让 OCR 兜底的输入框探测/右键/菜单全失败；切换会话才恢复，这就是「时好时坏」。③`_find_row_by_text` 把滚动命中的 rect 当控件传 `_right_click_row`（AttributeError 被吞），且后者返回 bool 却被 `_set_cursor(*pos)` 解包。④「引用最新一条」原本钉死页面加载时的 local_id，自己刚发的回复会让它退化成脆弱的历史文本定位 → 改为 `quote.latest` 意图，执行时右键真正最新。改这块前先只读查微信库原文字符、确认滚动失败会复位。
- **「关到托盘后卡死」与「@+引用只发 @」是两条独立确定性 bug**（2026-11-15 01:02~01:07 实测）：①微信点 X 关到托盘在 Win32 层是 `IsIconic=True`（160×28 伪矩形）或 `SW_HIDE`（visible=False，另有隐藏 `WxTrayIconMessageWindow`），**Qt accessibility 树只在可见窗口物化**；旧唤醒流程不管窗口状态、对托盘窗口反复写 gate byte → 树不重建且 Qt 输入系统被写挂（界面卡死），31s 超时后 `_get_uia()` 永久置 `_uia_tried` → 整场会话降级 OCR → 93s 失败。现修：`uia_driver._restore_window_visible()`（最小化 SW_RESTORE / 隐藏 SW_SHOW）、唤醒前先恢复、不可见**不打补丁**、单次等待真实写入上限 2 次；`guia.ensure_visible` 覆盖 SW_HIDE、`_find_minimized_main_window` 不再要求 visible、`_get_uia` 失败改 30s 冷却可重试。②`SenderThread._do_send` 的 @/引用是 `if...return` 互斥分支 → 组合时引用被静默丢弃却报成功；现走 `at_members(quote=True)` 同草稿（先建引用卡片、再逐个 @、只回车一次，**引用后绝不能 Ctrl+A/Delete**），UIA 不可用明确失败。另：`hasattr(gui,'at_members')` 对属性值为 None 返回 True，必须用 `callable(getattr(...))`。
- **发送链路已改为 fail-closed，别再加截图/OCR 兜底**（2026-11-15 09:52~09:57 实测，用户明确要求）：①关到托盘/最小化后 Qt 回收 UIA 树却把 accessibility gate 留在 1，普通热激活返回 `'already'` 什么都不写 → 干等 30s（日志「真实写入补丁 0 次」）；现用 `_hot_activate_accessibility(rearm=True)` 做受控 `1→0→1` 脉冲 + 同 PID 45s 限流，窗口不可见立即失败。②托盘恢复后 `render_rect` 是 160×28 伪矩形，OCR 兜底必然抛 `Coordinate 'right' is less than 'left'` 并白等 20~30s；现 `guia.OCR_FALLBACK_ENABLED=False` + `_require_uia()` 总闸，`send_msg/quote_msg/at_members/input_only/open_chat/open_chat_prefer_openim` 只走 UIA，失败直接判失败（命令行 demo 需显式 `WECHATAUTO_OCR_FALLBACK=1`）。③恢复后真实主窗句柄会变（实测 4000292→1378074），`_current_chat` 缓存 + `assume_open` 会让消息打进别的会话；现 `_rebind_if_window_changed()` 重绑清缓存 + 每次发送 `_confirm_target_chat()` 实时读 `uia.current_chat()`（企业微信不匹配拒绝二次 open_chat，免得开成同名普通好友）。④响应带 `data.chat_verified`，sender 只在 True 时把「已操作发送 + 数据库未确认」按 replied 处理，否则保持 pending 并提示核对收件人；组件层 DB 未确认文案有 6 种前缀（消息/引用/@消息/文件/图片/回复），别只匹配「消息已操作发送」。
- **关到托盘 = Qt hide()，不是 Win32 最小化，别再用 SW_SHOW 强行唤醒**（2026-11-15 11:30~11:35 实测）：①托盘态 `IsWindowVisible=False`，最小化 `IsIconic=True` 但 visible 仍 True；`SW_SHOW` 托盘窗口会让 Qt 内部与 Win32 状态不一致 → UIA 树死活不物化（16s+31s 两次超时），窗口卡成 `visible=True+iconic=True` 的 -32000 伪矩形（用户「界面不能动」），还会连打补丁把 Qt 输入写挂（同 PID 129s 内 6 次写 → 限流报「建议重启微信」）。②发送路径 + 后台预热巡检（每 15s `warm_up(30)`）轮流唤醒是补丁密集的主因。现修：`guia.is_tray_hidden()` + `ensure_visible()` 托盘态绝不 SW_SHOW/写补丁（第 7 轮起**发送路径**改为点击托盘图标自动唤起，只有唤起失败才 0 秒 return False）、`_last_open_error='tray_hidden'` 仅作兜底；`uia_driver._restore_window_visible()` 只 SW_RESTORE 真最小化、托盘态返回 False + `_tray_hidden_detected`，`_wake_and_wait_ready`/`ensure_window` 见标记即失败不写内存；`sender._prewarm_once()` 托盘态静默跳过并给「点任务栏右下角微信图标」提示。③真最小化仍要恢复（SW_RESTORE 实测有效，别一起禁）；从托盘点开后必须清 `_uia`/`_current_chat`/`_last_input_box` 并重绑句柄。④rearm 的 `1→0→1` 是 **2 次写内存**，计数按 2，且距任何真实补丁 ≥45s。
- 微信语音**异步落库**：消息行先到、`media_*.db VoiceInfo.voice_data` 后到；转写失败须进 `voice_retry.py` 退避队列（5/15/45/120/300s），失败直接丢弃会漏商机。

- **微信 UIA 树会被回收，`_find_main()` 仍能拿到只剩 Qt 外壳的窗口**（`MMUIRenderSubWindowHW`+`QWidget` 两子控件）；此时任何 Edit/Text 查找都超时，表现成「无法定位会话」。判定锚点用 `MainView`（`is_ready()`），首次物化实测 15~30 秒。
- **4.1.15.56 UIA 树物化 = 环境变量 + 补丁缺一不可，但补丁必须限流**（2026-11-14 两次实测修正）：进程带 `QT_ACCESSIBILITY=1` 启动后树**仍不随启动物化**，必须再打 `_wake_accessibility()` 热激活补丁（gate byte 0→1）才在约 1s 内物化；不带环境变量时补丁无效。**90 秒内对同一进程补丁 4+ 次会把 Qt 输入系统写挂**——症状：渲染正常、WM_NULL 正常、CPU 0%，但 SendInput/PostMessage 鼠标全被吞、SetWindowPos 被拒，只能重启微信。已加类级限流（同 PID 冷却 20s、上限 5 次、300s 重置、失败不计数），超限走 OCR 兜底。改这块前先看 TestWakeAccessibilityThrottle。
- **微信重启后 sender 会 0 秒报「微信未登录」**：`WeChatGUI` 缓存 `main_hwnd`，重启后 `is_alive()`（只查 IsWindow）恒 False，原代码 `_ensure_gui` 直接判死。已加 `rebind()`（重新评分定位主窗口+刷新 render/pid+清空会话与 UIA 缓存），`sender._ensure_gui` 死句柄先 rebind 再失败。别再往 `_ensure_gui` 加「is_alive False 就报错」的短路。
- **窗口识别必须有进程硬门槛，评分不能替代身份**（2026-11-14 实测事故）：微信退出后，EditPlus 打开的「微信客服开发-记事本.txt」窗口（标题含「微信」+5、尺寸+2=7 分过线）被绑成微信主窗口，自动化点击/键盘全落到 EditPlus 上，用户肉眼可见。修复：guia `_is_wechat_process`（进程名 startswith('weixin')，查询失败返回 None 不否决防误杀）在 `_looks_like_main_window` 与 `_find_main_window` 一票否决。改窗口识别逻辑时，标题/类名只能用于同进程内区分，进程身份必须先行。
- **商机类型能否命中，八成取决于该类型的 `description`，不是 Prompt 模板**（2026-11-13 实测）：`build_system_prompt` 的总纲是「是否表达明确的业务合作意向（采购/委托/询价/求供）」+ balanced「有标的物+意向动作」+ 原则「闲聊一律 hit=false」+ points 只收标的/数量/价格 + direction 只有 buy/sell——非交易型类型（投诉/售后/求助）在这套范式里**天然落空**。只把旧类型描述扩成「命中特征词清单 + 豁免句（如『没有报价/数量/标的物不影响命中』）+ 字段约定（type/points/direction 怎么填）」，实测 7 条投诉全命中、6 条闲聊全不命中、配件交易仍归「汽车配件」，无需改代码。新加类型别再只写「判断是否有 X」。

- **群商机回复分「群内 / 私信」**（第 15 批）：`ReplyRequest.target`（session|sender）；私信只能发给发送人本人，且必须 `is_friend`（`wechatauto/db.py`：local_type 3=好友、1 非群/公众号/小程序/系统号=仅聊天好友、5-7=企业微信，0=非好友交互者→False，delete_flag=1→False）。前端私信按钮非好友置灰。**手动确认模式下 @ 不生效**（微信 @ 要输入时从弹层选人，`input_only` 只粘贴文字），UI 用提示条+「改为自动发送」兜住；私信回复不许带 at/quote（引用的消息在群会话里）。@ 必须用`list_group_members` 的当前群昵称，商机里存的旧名改名后 @ 不到。
- **授权开关 v2 是 fail-closed**：`license.enabled` 任何取值都需要授权，只有等于厂商测试口令（明文或 SHA256 指纹）才关闭校验；`KEFU_LICENSE_MODE=enforce`（env，`run.py --license` 设它）优先级最高、无视口令。切模式只用 `python run.py --license-dev 口令`（必须现场出示，客户拿到程序也关不掉）/ `--license-on`。口令明文不写进 kefu-system/ 任何文件，代码里只有 `DEV_TOKEN_SHA256`。别再把 `0/false/空` 当关闭开关。
- **授权（license）机器码不能用 WMI**（2026-11-13 实测）：本机 WMI 仓库已损坏（`Win32_BaseBoard` 报「无效类」），而 WMI 被系统更新打坏并不罕见——一旦 WMI 参与机器码哈希，坏一次全体客户授权同时失效。现用注册表 `MachineGuid` + Win32 `GetVolumeInformationW` 卷序列号（<10ms、不落盘缓存），WMI 只作排障展示。许可证用 Ed25519 签名（私钥只在服务端，客户端内置公钥表 `PUBLIC_KEYS`），离线宽限 7 天靠 `last_ok_at`，防时钟回拨靠 `max_seen_ts`。接口契约见 `kefu-system/docs/授权服务接口文档.md`，模拟服务器 `tools/mock_license_server.py`（管理台 /admin）。

- **不要并发操作微信 UIA；启动预热必须保留**（2026-11-13/14 实测）：微信 UIA provider 单线程，任何后台 UIA 线程都要持 `_gui_lock`。2026-11-13 的 68s 事故根因是预热线程没持锁；2026-11-14 已重新启用启动预热（main.py `sender.start(prewarm=True)`），`_prewarm` = `_ensure_gui()` + `WeChatGUI.warm_up()`（走 warm_tree，不激活窗口、不点搜索）全程持锁、抢不到即弃。UIA 树首次物化 15~30s 必须在启动时做掉——实测首次发送「打开会话 25.4s」的主体就是它，不要因「怕并发」再关预热。

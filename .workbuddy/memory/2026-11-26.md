## 已实施：升级后自动重启 + 状态可见性（A/B/C/D，未 commit）

用户点名四件事，全部落地：

- **A 前端不再把 `installing` 当终态**：`UpdatePanel.tsx` 引入「等自动重启」态，每 2s 轮询 `/status`，重启期间的连接失败**不当错误**；每轮驱动 `update-check` 重取；完成判据只认后端自报 `current_version` 变化 → 「升级完成，当前版本 vX」；5min 未变 → 「程序未能自动重启，请退出托盘后重新打开」。另外 `useUpdateCheck` 加 `refetchOnWindowFocus: true` 覆盖 `main.tsx:14` 的全局 `false`（`staleTime` 5min 天然限流），解决「页面挂着最长 12h 不重查」。
- **B 升级完成托盘气泡**：`launcher._notify()` 用 ctypes 手搓 `NOTIFYICONDATAW` + `NIF_INFO`（pywin32 的 6 元组 `Shell_NotifyIcon` 带不了 szInfo），失败退回日志 `_notify_or_log`。
- **C 启动器日志落盘**：`_log()` 同步追加 `data/launcher.log`（`YYYY-MM-DD HH:MM:SS` 前导，超 1MB 轮转留 `launcher.log.1`），落盘排在 GUI 缓冲之前、IO 异常内部吞掉——落不了盘也必须保住日志窗口。
- **D 增量升级也自动重启**（原先只能人工重启）：新增接力文件协议 `data/update_handoff.json`（`app/update_core.write_handoff/read_handoff/clear_handoff`），`kind=restart` 由后端 `apply()` 的 app 分支与 `updater.py` 增量尾部写入，`kind=notify` 由 `reconcile_full_install()` 确认全量落地时写入；`launcher._start_handoff_watcher()` 守护线程 2s 轮询、读到即删，`restart` 走 `_stop_backend → _read_port → _start_backend → _port_ready(60s) → _open_ui → 气泡`。

安全护栏（都写了测试）：
- 守卫 `at < _state["started_at"]`：属于上一个启动器进程的请求绝不执行，否则冷启动就重启刚起来的自己。
- 守卫 `now - at > 15min`（`HANDOFF_TTL_SEC`）：半途失败留下的陈旧请求会把正在下载 284MB 全量包的后端无辜杀掉。
- 读到即删（一次请求只执行一次）；坏 JSON / 非 int `at` / bool `at` / 未知 `kind` 全部 fail-safe 忽略。
- `MENU_EXIT` 先置 `_state["exiting"]=True` 再 `_stop_backend()`：接力线程最坏阻塞 30s，不立旗会在用户退出后把后端再拉起来（孤儿进程）。
- apply 失败分支不写请求（`test_apply_aborts_on_nonwhitelist_bundle_root_entry` 锁死）。
- 轮询线程任何异常只记日志继续，与 `_drain_loop` 同一取舍。

## 已知限制（必须对用户讲清楚）

**一跳延迟**：`launcher.pyc` 在 pythonw 内存里执行。增量升级能把新 `launcher.pyc` 写进安装根（`install_bundle_root_files`），但那一刻跑的还是旧启动器，旧启动器不认识接力文件——所以本次发布之后的**第一个**增量仍需人工重启一次，此后自动。全量升级的气泡同理（新启动器才有）。

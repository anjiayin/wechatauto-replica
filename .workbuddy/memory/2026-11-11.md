## 【根因确认】清理误删一天 = cutoff 用 T 分隔、created_at 用空格分隔
- 用户在设置页「立即清理·保留 1 天」后，11-02~11-10 的 analysis_logs/opportunities 全被删光（这就是"AI 账单只有今日有数据"的真因，不是没记库）。
- 根因：`delete_older_than` 用 `datetime.now().isoformat()` 生成 cutoff = `2026-11-10T11:00:53`，而 created_at 由 `datetime('now','localtime')` 落地 = `2026-11-10 23:32:22`。SQLite 按 TEXT memcmp，`' '`(0x20) < `'T'`(0x54) → **cutoff 当天的记录全部被判为"早于 cutoff"删掉**。实测 `SELECT '2026-11-10 23:32:22' < '2026-11-10T11:00:53'` = 1。
- 修复：cutoff 全部交给 SQLite `datetime('now','localtime','start of day', ?)`，参数 `-(days-1) days` → 语义「保留最近 N 个自然日（含今天）」：N=1 → 今天 00:00；N=2 → 昨天 00:00；N=30 → 29 天前 00:00。`_purge_modifier` 是 cutoff/count/delete 三处唯一口径来源。
- 次级根因（为什么清理没日志）：`LOG_MAX_BYTES=2MB` 超限后 `RotatingFileHandler.doRollover()` 在 Windows rename 失败（被 pytest 进程占用），基类已 close stream 且异常被 handleError 吞掉 → **此后整进程不写日志**（现场：库写到 10:59，日志停在 10:50）。修复 `app/main.py::SafeRotatingFileHandler`（失败重开流继续追加）+ `setup_logging` 幂等（`_kefu_file`/`_kefu_console` 标记）+ 启动打印日志路径与大小。
- 安全化：`POST /api/system/purge` 支持 `dry_run`（预览条数不落库）、`PurgeResult` 增 `dry_run`/`cutoff`、真删后写 `runtime.last_purge`(JSON)、新增 `GET /api/system/purge/last`；前端改「预览 → Dialog 二次确认 → 真删」并显示「上次清理」。
- 验证：359 passed（新增 14 项）、tsc、vite build 全通过；QA 独立复验（对照实验证明原生 handler 会丢 3 条、Safe 版不丢）→ 路由 NoOne。
- 遗留：真实库需重启才建 ai_usage 并回填 95 条；11-10 丢失明细不可恢复。P3 建议：跨零点确认框需重新预览、轮转失败计数可暴露到 /api/status、商机清理弹窗补"引用会置空"文案。

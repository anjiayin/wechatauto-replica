## 【根因确认】清理误删一天 = cutoff 用 T 分隔、created_at 用空格分隔
- 用户在设置页「立即清理·保留 1 天」后，11-02~11-10 的 analysis_logs/opportunities 全被删光（这就是"AI 账单只有今日有数据"的真因，不是没记库）。
- 根因：`delete_older_than` 用 `datetime.now().isoformat()` 生成 cutoff = `2026-11-10T11:00:53`，而 created_at 由 `datetime('now','localtime')` 落地 = `2026-11-10 23:32:22`。SQLite 按 TEXT memcmp，`' '`(0x20) < `'T'`(0x54) → **cutoff 当天的记录全部被判为"早于 cutoff"删掉**。实测 `SELECT '2026-11-10 23:32:22' < '2026-11-10T11:00:53'` = 1。
- 修复：cutoff 全部交给 SQLite `datetime('now','localtime','start of day', ?)`，参数 `-(days-1) days` → 语义「保留最近 N 个自然日（含今天）」：N=1 → 今天 00:00；N=2 → 昨天 00:00；N=30 → 29 天前 00:00。`_purge_modifier` 是 cutoff/count/delete 三处唯一口径来源。
- 次级根因（为什么清理没日志）：`LOG_MAX_BYTES=2MB` 超限后 `RotatingFileHandler.doRollover()` 在 Windows rename 失败（被 pytest 进程占用），基类已 close stream 且异常被 handleError 吞掉 → **此后整进程不写日志**（现场：库写到 10:59，日志停在 10:50）。修复 `app/main.py::SafeRotatingFileHandler`（失败重开流继续追加）+ `setup_logging` 幂等（`_kefu_file`/`_kefu_console` 标记）+ 启动打印日志路径与大小。
- 安全化：`POST /api/system/purge` 支持 `dry_run`（预览条数不落库）、`PurgeResult` 增 `dry_run`/`cutoff`、真删后写 `runtime.last_purge`(JSON)、新增 `GET /api/system/purge/last`；前端改「预览 → Dialog 二次确认 → 真删」并显示「上次清理」。
- 验证：359 passed（新增 14 项）、tsc、vite build 全通过；QA 独立复验（对照实验证明原生 handler 会丢 3 条、Safe 版不丢）→ 路由 NoOne。
- 遗留：真实库需重启才建 ai_usage 并回填 95 条；11-10 丢失明细不可恢复。P3 建议：跨零点确认框需重新预览、轮转失败计数可暴露到 /api/status、商机清理弹窗补"引用会置空"文案。

## 语音消息转文字（本地离线 SenseVoice）接入商机分析
- 现状：`_on_message` 对非文本一律 skipped，语音只显示 `[语音]`，商机漏判。
- 数据链路（已实测）：`media_*.db` 的 `VoiceInfo.voice_data` 存 SILK v3（本机 2511 条/676 条 local_type=34 消息）；`MediaDownloader.download_voice(user, local_id)` 可取（首次触发 media 库解密约 13s，之后增量）。语音消息 `message_content` 是 **zstd 压缩**（`WCDB_CT_message_content` 标记），解压后是 `<voicemsg>` XML。
- 关键结论：**微信本地不缓存语音转文字结果**（全库无 VoiceTrans/asr 类表），所以必须自己识别。
- 解码：`tools/silk_v3_decoder.exe`（kn007/silk-v3-decoder 预编译，179KB）`silk_v3_decoder.exe in.silk out.pcm -Fs_API 16000` → 16k/16bit/mono 裸 PCM，0.005s。GitHub raw 被墙，**ghproxy.net 镜像可用**；pypi/清华源无 pilk 且无编译器。
- 识别：`sherpa-onnx` 2.0.1（cp313 wheel 从 pypi 直下）+ **SenseVoice-Small int8** 模型（`hf-mirror.com/csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`，228MB，15 秒下完）。**2.0.1 API 只有 `accept_waveform(16000, float32)`，没有 `read_wave`/`accept_wave_file`**。
- 实测：模型加载 2.4~5s（单例常驻）；3s 音频 0.5s，26s 音频 1.5s；6 条真实微信语音识别全部准确（含 26s 教务对话、20s 二手车闲聊）。
- 用户现有 AI（scnet GLM-5.3-Flash，33 个模型）**无语音转写能力**，不能复用。
- 实现：`app/voice_asr.py`（VoiceTranscriber 单例/懒加载/RLock/超时上限/`ensure_model` 从 hf-mirror 下载 .part→os.replace）；`db.voice_texts` 缓存表（PK username+local_id，**不在 _PURGE_TABLES**）；`wechat_service.transcribe_voice` 缓存优先；`_on_message` 语音成功→`[语音] 文本` 进聚合窗口；`_fetch_messages_once` 只批量查缓存**绝不在请求线程识别**；`pipeline._topup_voice_lines` 每单元最多补 3 条。
- 关键设计取舍：**失败不写缓存**（模型未装/微信未下载是可恢复状态，写负缓存会导致装好模型后永远看不到文字）；`duration_ms` 只统计解码+识别，剔除模型加载（否则首条 12.7s 虚高）。
- 验证：全量 **411 passed**；QA 独立复验真实端到端——冷启 6.95s / 热 1.37s / 缓存 0.00008s；取 200 条含 7 条语音的会话耗时 0.184s 且识别调用次数 0（请求路径零阻塞）；降级 5 种场景全覆盖。路由 NoOne。
- 迭代修的两处（QA 挖出）：① `_topup_voice_lines` 预算原只对成功扣减 → 10 条全失败时调 10 次、白花 14s，改为「尝试即扣减」；② `duration_ms` 含模型加载 → 改 `decode_ms + recognize_ms`（threading.local 存分段计时）。
- 上线：**必须重启服务**才会建 `voice_texts` 表；模型已就位 `data/asr_models/`（229MB，data 在 gitignore）；`tools/silk_v3_decoder.exe` 仍 untracked，新机器部署建议入库，否则靠 ghproxy 联网兜底。

## 语音转写失败修复：自动补转写队列（消息先到、音频后到）
- 用户实测：连发 2 条语音，第 1 条识别成功，第 2 条报「未找到语音数据（微信可能尚未下载该语音）」。
- 根因（真库验证）：微信语音是**异步落库**——消息行（message_*.db）先到，音频（media_*.db VoiceInfo.voice_data）要过一段时间/客户端触发下载后才写入。Listener 秒级轮询导致首次转写几乎必然太早；filehelper local_id=114 在 17:11:37 失败，17:20 时同一查询已能取到 4236 字节并识别成功。**失败直接 return 丢消息**才是 bug：这条语音永远不会再被分析。
- 实现（补转写队列）：
  - 新增 `app/voice_retry.py`：`VoiceRetryQueue` 单线程 + 条件变量，退避 (5/15/45/120/300)s 共 5 次（累计约 8 分钟）；同 (username,local_id) 去重；上限 200 丢最旧；回调异常吞掉；**服务停止时在途任务只放弃、不落终态**（曾修过 stop 被误判成"重试用尽"的分支）；status() 供运维展示。
  - `wechat_service`：`_handle_voice_failure` 只对 `MSG_ASR_NO_VOICE`（可恢复）入队，配置类失败（开关关/模型未装/库不可用）不重试；先落占位日志（skipped + "已加入自动重试"）再入队；`_on_voice_retry_success` 就地回填原日志为 ok 并把消息快照重新 `aggregator.add`（重新分析，商机不漏）；`_on_voice_retry_failure` 终态文案指引"在微信播放后点重新识别"；新 `retry_voice()` 手动重试（无快照时用 `get_message_row` 重建消息入窗口）。队列在 `start()` 启动、`stop()` 停止。
  - `db.py`：analysis_logs 迁移加 `voice_local_id` 列（前端重试定位）；`update_analysis_log_voice()` 回填；list SELECT 补列。
  - API：`POST /api/voice/retry`（username+local_id+可选 log_id），内部异常也返回结构化错误不 500。
  - 前端：AnalysisLogs 对「语音转写失败」行显示「重新识别」按钮（替代无意义的漏判修正按钮），成功 toast 显示转写文本；types.ts 加 `voice_local_id`/`VoiceRetryResult`。
  - 文案：`MSG_ASR_NO_VOICE` 改为「微信尚未下载该语音（在微信里点开播放一次即可）」。
- 设计取舍：不主动 UI 自动化点播放（会出声/抢焦点）；重启后内存队列丢失，靠手动重试兜底。
- 验证：新增 `tests/test_voice_retry.py` 23 项（真实线程+0.02s 退避）；真实数据端到端——114 `retry_voice` 返回「那家有机油奶香。」（识别有误差，属模型层面）；不存在的 local_id 3 次重试后 exhausted=1、日志回填终态含手动指引。全量 **434 passed**，`tsc` + `vite build` 通过。**需重启服务生效**。

## 诊断：启动后「微信窗口不可用」但预热已完成

用户现象：服务启动日志显示「微信预热完成（24.4s）」，前端顶栏仍显示红标「微信窗口不可用」，刷新无效，过较长时间后自行变绿。

结论（代码层可证的部分）：
- 顶栏标签只由 `App.tsx:276` 的 `status?.wechat.visible` 驱动，前端每 5s 轮询 `/api/status`，刷新页面不起作用。
- 数据源 `router_system.py:112-113` → `wechat_service.py:3292 probe_wechat_window()`：`ctypes.windll.user32.FindWindowW(None, title)`，候选标题只有 `_WX_MAIN_TITLE_CANDIDATES = ("微信", "WeChat")` 两个，**精确匹配、不包含、不校验进程/可见性**。
- 预热走 `main.py:243 sender.start(prewarm=True)` → `warm_tree()`，与状态探测**完全独立、不共享状态**；预热成功 ≠ 状态标签变绿。
- 实机复现探测的脆弱性：当前同时存在两个标题恰为「微信」的顶层窗口——`HWND=198910 / PID=11828 / Chrome_WidgetWin_0 / 全屏 1920x1015`（WeChatAppEx 小程序宿主）和 `HWND=263324 / PID=3152 / Qt51514QWindowIcon`（真正微信主窗）；`FindWindowW` 返回 Z 序第一个，可能绑错窗口。业务侧 `guia.py:506 _looks_like_main_window()` 用「进程名 weixin 一票否决 + 标题含关键词 + 类名 + 可见 + 尺寸」评分，比状态探测健壮得多。
- 触发条件判断：微信 4.x 标题随未读消息数/当前会话/托盘恢复中间态变化（如「微信 (N)」），精确匹配一旦对不上即返回 False；标题恢复后下一个 5s 轮询自动变绿。当时的实际标题**未被记录**（probe 失败分支没有日志），这一具体触发点属推断，已建议加失败时标题日志取证。

## 实施：full 包自动静默重装能力（路径 B）
- 背景：跨版本用户被退回 full 包（Inno Setup exe），旧链路却把 exe 当 zip 解压 → BadZipFile。目标让两条更新链按类型分流。
- `kefu-system/app/update_core.py`：新增纯函数 `is_full_package`（type=='full' 大小写不敏感）、`full_install_args`（/VERYSILENT /NORESTART /SUPPRESSMSGBOXES + /CLOSEAPPLICATIONS /RESTARTAPPLICATIONS）、`launch_full_installer`（detached Popen，CREATE_NEW_PROCESS_GROUP|DETACHED_PROCESS，DEVNULL stdio，**绝不 wait/communicate**，异常吞掉返回 False）。
- `kefu-system/app/update_service.py`：`download()` 按类型落盘 `full-{v}.exe` / `app-{v}.zip`，`_job` 加 `package_type`；`apply()` 二次验签后重新 pick_package，类型漂移 fail-closed，full 分支复核 size+sha256 后 detached 拉起安装器，**不切 junction/不写 current.json/不动 bundle 根**（安装器负责，data 保留）。返回体加 `full_install: True`。前端 UpdatePanel 对 need_restart/applied 已有通用处理，无需改前端。
- `packaging/updater.py`：两处 import 补 `is_full_package`/`launch_full_installer`；`run()` full 分支落盘 .exe、下载校验后 detached 拉起，启动失败返回新码 8，跳过解压/junction/current.json。
- `kefu-system/tests/test_updater.py`：新增 10 个用例（类型判定、参数顺序、detached 不 wait、Popen 异常、托盘 full 成功/失败码、后端 full apply 成功/sha 不符中止）。
- 验证：定向 test_updater+test_update_service+test_core = **167 passed**；**全量 1793 passed / 2 xfailed / 809s**（较上次 1784 多 9 个，即本次新增用例；此前记忆里的 1234/1784 基线均已过时）。
- **关键约束（鸡生蛋）**：新能力在版本层代码（update_core/update_service）+ updater.pyc 里。要让跨版本老用户走 full，必须**先用 app 增量包把新客户端下发到位**（app 包 from_versions 不设/覆盖老版本），再改 `--from-version` 让指定老版本退回 full；否则老客户端没有 full 处理能力，拿到 exe 仍按 zip 处理。
- Inno Setup 参数经官方文档核实：`/CLOSEAPPLICATIONS` `/RESTARTAPPLICATIONS` `/FORCECLOSEAPPLICATIONS` 均为真实开关，静默模式下 CloseApplications 默认开启。

## 事故：1.2.9 升级后界面仍显示 1.3.0 + 误报「已是最新版本」
- 现象：bump 1.3.1 → build_p1 → build_installer → build_release(seq=1310) 发布后，1.2.9 客户端升级成功，但顶栏 Chip/系统更新页 Chip 显示 v1.3.0，正文却显示「当前版本: v1.3.1 · 最新版本: v1.3.1」，同时提示「当前已经是最新版本（v1.3.0）」。
- **根因：漏跑前端 build**。用户按我上一轮建议「本次只改后端，跳过 npm build」，但 `--bump 1.3.1` 会改 package.json/lock；`vite.config.ts:12,42` 在构建期把 version.txt 注入 `__APP_VERSION__`，没重新 build → `frontend/dist` 仍是 1.3.0 的 JS（实测仓库 dist grep 只有 1.3.0）。build_p1 `COPY frontend/dist` 把旧 dist 打进 1.3.1 版本层 → 前端硬编码版本 1.3.0，后端 `config.py` runtime 读 bundle 根 version.txt=1.3.1 → 两个「当前版本」打架。后端 check 判 current=1.3.1 == latest=1.3.1 → action=none 是**正确**的；误导性文案（v1.3.0）来自前端常量，且 `update_available` 无 channel/sequence 问题。
- **铁律修正**：`version_sync.py --bump` 之后**必须** `npm --prefix kefu-system/frontend run build`，即使本次只改后端——只要版本号变了，前端构建期常量就必须重建。`--check` 只校验源码侧 6 处字面量，**不覆盖 dist**（dist 是 gitignore 的构建产物）。
- 补救：重新 build 前端 → build_p1 → build_installer → build_release(--sequence >1310，如 1311)；已升到 1.3.1 的机器版本号相同不会再提示，需手工重装新 exe 或再 bump 1.3.2。

## 已实施：重启后免重下的全量安装重试（未 commit）
- 补上原投诉里唯一没解决的行为缺口：「手工重启服务也不能触发全量升级」。根因不是重启逻辑，而是 `UpdateService._job` 是**进程内存态**——重启后归零，`apply()` 又要求 `state=="done"`，界面只剩「重新下载」，用户被迫重下 284MB；而 `full-<ver>.exe` 其实一直留在 `data/update/`（升级不清理 data）。
- `update_service.py` 新增 `UpdateService._hydrate_full_retry()`，在 `status()` 取锁之前调用：`state=="idle"` + pending 未生效 + `bundle_root()` 非空 + `data/update/full-<pending>.exe` 存在且非 0 字节 → 把 `_job` 补成 `{state:"done", version:pending, package_type:"full", done:total:size}`。前端现成的 `state === 'done'` 分支直接给出「安装并重启」，**不需要新增接口字段**，也无需 `types.ts` 改动。

- 边界（单测锁死）：0 字节半成品不补位；包被清理不补位；`APP_VERSION >= pending`（已装上，等启动自检确认）不补位；`state` 非 idle（下载中/installing/error）绝不覆盖；开发态 `bundle_root()` 为 None 直接返回。`_lock` 是 `threading.Lock` 不是可重入锁——`status()` 必须在取锁**之前**调用补位。

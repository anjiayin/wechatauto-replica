## 23:40 修复：Ctrl+C 卡在 "Shutting down"（用户报第 2 次）
- **活体证据**：用户那次进程 PID 16376（conda python，22:49 启动）当时还活着——
  8766 不监听、库仍在写、还有 AI 443 连接，说明 uvicorn 进了 shutdown 但
  lifespan shutdown 没跑，微信监听线程照旧轮询。
- **根因两层**：① uvicorn 0.54 的 `timeout_graceful_shutdown` 默认 None =
  无限等 `_wait_tasks_to_complete()`，**在 lifespan.shutdown() 之前**；一个卡住的
  同步请求（AnyIO 线程池）就能永远卡住，关闭逻辑一次都不跑。
  ② 即使 uvicorn 返回，解释器退出还要等 **non-daemon 的 AnyIO worker**，
  表现为停在 `threading._shutdown()`。
  实测复现（`D:/tmp/uvicorn_ws_shutdown_repro.py`）：空闲 0.2s / 开 WS 0.2s
  （WS 不是元凶）/ 卡住请求 >20s / 卡住请求+timeout=5 → 5.2s。
- **修复 `run.py`**：`timeout_graceful_shutdown=5` + `_KefuServer.handle_exit`
  先挂 20s 看门狗（抓全线程 Python 栈→控制台+`data/shutdown-dump-*.log`→
  `os._exit(130)`）+ 收尾 `os._exit(code)` 跳过 `threading._shutdown`。
  新增 `tests/test_shutdown_watchdog.py`（8 例）。端到端实测 Ctrl+C 后 5.2s 返回。
- 经验：**Python 服务的 Ctrl+C 卡死先看两个默认值**——uvicorn 的
  `timeout_graceful_shutdown`（None=无限）和解释器对非 daemon 线程的 join。
  线上诊断技巧：`Get-Process -Id <pid> | Select Threads` 看哪个线程 CPU 在涨，
  `Get-NetTCPConnection -State Listen` 看监听是否已关（关了=已在 shutdown）。
  本机 WMI 坏了，`Get-CimInstance Win32_Process` 报「无效类」，改用 Get-Process。

## 客户机双微信：回复发错实例（一次只监控一个账号，未 commit，未真机验证）

现场：客户机同时跑两个 `Weixin.exe`（同一 `Weixin.exe` 路径 `start` 两次）。界面能加监控对象、能抓消息，但无法确认联系人属于哪个微信，回复落到了「不是接收消息的那个微信」上。

根因两条：
1. 账号选择靠 `WeChatDB._pick_account()` 按 `.db` mtime 选最新目录，无身份确认，双开时可能读 A 存 B；
2. 发送 `WeChatGUI()` 按「最大/最高分窗口」任选实例，`WeChatUIA.wake()` 走 `weixin://` 会拉起默认账号。

用户拍板：**一次只监控一个账号**（设置页显示当前账号、可切换），现在开始改。

### 已实施

- **账号 ↔ 实例绑定**（`wechatauto/db.py`）：新增模块级 `enumerate_weixin_pids()`；`WeChatDB.find_account_pid(pids, strict=False)`：单实例非 strict 直接返回；strict（用户指定账号目录）仍校验——cfg wxId 快速匹配，读不到再 `_master_matches_account()` 用主密钥对账号库页 1 HMAC 强校验，结果三态 `True/False/None`（`None`=无库可读，不阻断）；多实例逐个 wxId/主密钥匹配，仍无法确认返回 `None`（调用方必须 fail-closed）。
- **G/UIA 定向**：`WeChatGUI(pid=...)` 窗口枚举/评分/最小化恢复/rebind 全部只认目标 PID，构造时 PID 不符直接抛错；`WeChatUIA(hwnd=, pid=)` 过滤 `_wechat_hwnds`/托盘恢复，绑定实例时**绝不** `wake()`（避免 `weixin://` 拉起默认账号）；目标实例无窗口时 `ensure_window` 返回 False，不新开实例。
- **服务层**（`kefu-system/app/wechat_service.py`）：`configured_account/effective_account/account_list/account_binding`（绑定缓存 15s）；`switch_account()` 只重开 Listener（`_open_listener_locked`），保留 vision/ASR/sender/flush 线程；`_reset_account_caches()` 清 name/alias/corp/contact/group/media/binding 缓存；指定账号目录不存在时降级给出可操作原因，绝不悄悄回退。
- **发送 fail-closed**（`sender.py`）：绑定注入 `set_wechat_binding_provider()`；多实例未映射、或 pinned 单实例账号不符 → 不建 GUI、返回明确原因；GUI 缓存按账号/PID 变化重建；`SendTask.account` 入队盖章，`_process_locked` 先比对当前账号，切换账号后旧账号排队回复直接取消（防新账号同名联系人收错消息）。
- **API/状态**：`GET /api/wechat/accounts`、`POST /api/wechat/account`；`/api/status` 的 `wechat.account` 带 account/wxid/nick_name/pid/instance_count/mapped/pinned/reason。
- **前端**：顶栏显示「账号：昵称/wxid（已绑定/未确认，共 N 个微信）」，无法确认时全局红色横幅；设置 → 监控对象页顶部常驻「当前监控账号，联系人来自该账号」；设置 → 数据与账单新增「监控微信账号」选择/切换/刷新 + 当前 PID/实例数/错误提示；切换后失效 status/monitor-targets/session-candidates/sessions/image-key-status 查询（图片密钥按账号隔离）。

## 客户机反馈第二轮：5 个微信误报 / 选中的微信未确认 / 账号昵称 / 撤回 XML（未 commit）

用户真机截图四个问题：

1. 设置页账号下拉只有 wxid（`wxid_hu7azjb674f721 · 当前` 等），分不清是谁 → 选项要带微信昵称；
2. 实际只开了一个微信，界面却「检测到 5 个微信」；
3. 「设置的要监控的微信」显示「未确认实例」（自动回复被暂停）；
4. 撤回消息在消息列表里原样显示 `<sysmsg type="revokemsg">…` XML。

### 根因（已在真机数据上验证）

- **5 个微信**：微信 4.x 是多进程架构，1 个主进程（pid 11800）+ 4 个同名渲染/工具子进程（12676/13244/13248/17784，父进程都是 11800）。`enumerate_weixin_pids()` 原来把所有 `weixin.exe` 都算实例。
- **未确认实例**：该微信版本 `extract_master_key_from_cfg()` 对全部 5 个 pid 都返回 None（内存锚点不匹配），多实例路径没有凭据 → fail-closed。实测主进程 11800 的 `open_files()` 持有 `E:\xwechat_files\wxid_hu7azjb674f721_ac0e\db_storage\...` 292 个句柄（0.76s），子进程没有账号句柄 → 可用「打开文件句柄」做版本无关的账号 ↔ 实例匹配。
- **无昵称**：`list_accounts()` 只有目录名/wxid（昵称需解密各账号 contact.db，未登录账号拿不到）；只有当前账号能通过 `get_self_info()` 读到昵称。
- **撤回 XML**：全项目无 revokemsg 解析；`content_format.format_content("系统消息", …)` 原样透传。

### 已实施

- **实例枚举只算主进程**（`wechatauto/db.py::enumerate_weixin_pids`）：父进程名也是 weixin.exe 的视为子进程剔除；全被判成子进程的极端情况回退全量（宁可多报不误杀）；psutil 不可用仍走 tasklist 全量兜底。真机实测由 5 → `[11800]`。
- **句柄信号确认账号归属**（`db.py::_pid_account_match` + `find_account_pid` 改造）：
  - `_pid_account_match(pid)`：打开文件里有当前账号目录 → True；只开着其它账号的 `db_storage` → False；无句柄/读不到 → None。
  - `find_account_pid` 三级信号：句柄 True 直接命中（不读进程内存）；其次 cfg wxid；再次主密钥 HMAC。句柄 False 的进程从后续候选中排除；strict 单实例句柄 False → None（明确不是所选账号）；自动模式单实例仍直接返回、不探测句柄（零额外开销）。真机验证：11800→True、子进程→None、换其它账号→False。
- **账号昵称**：新增设置键 `runtime.wechat_account_nicks`（JSON：账号目录 → 昵称）；`_compute_account_binding()` 读到当前账号昵称即落库（仅变化时写）；`account_list()` 用昵称表 + 最近绑定缓存回填 `nick_name`，设置页下拉自动显示「昵称（wxid）· 当前」。
- **横幅去重**：前端不再拼接后端 `reason`（它本身就是整句说明，用户截图出现两遍）；App 全局横幅 / 设置页当前账号提示 / 监控对象页顶部提示统一按 `instance_count`/`pinned` 现场拼一次，带账号昵称。
- **撤回消息友好化**（`app/content_format.py::_format_sysmsg`）：识别 `<sysmsg>`（支持 XML 声明 / 群发送者前缀 / `<msg>` 包裹），优先 `replacemsg`、其次 `content`，输出客户端同款纯文本（如 `"L" 撤回了一条消息`）；revokemsg 正文不含「撤回」时补 `[撤回消息]`；普通系统文本原样；未知系统 XML 去标签兜底、绝不透传原始 XML。

### 验证

- `test_multi_account_routing.py` 新增：句柄映射/全其它账号 fail-closed/strict 句柄命中跳过内存扫描/strict 句柄否定拒绝/自动模式不探测；`_pid_account_match` 五种句柄场景；`enumerate_weixin_pids` 单主+4 子、双开两主、无微信、全子回退；昵称落库/列表回填/绑定缓存兜底。
- 新增 `tests/test_revokemsg_format.py`：截图原文 content 变体、replacemsg 优先、XML 声明、群前缀、`<msg>` 包裹、无「撤回」补前缀、标成文本类型仍解析、纯文本/坏 XML/未知 XML/其它 sysmsg。
- 定向回归：multi_account + revokemsg + session_start_filter 62 passed；api/core/feedback2/feedback3/summary_qa/batch6/qa_ux 331 passed；`tsc --noEmit && vite build` 通过（dist 已重建 index-D1-c_DrO.js）。
- 真机数据 smoke：`enumerate_weixin_pids()` → `[11800]`；`_pid_account_match(11800)` → True（监控账号）/ False（换成旧账号）；子进程 → None。
- 全量套件结果：见本轮后续记录（运行中）。

### 已知限制

- 从未监控过的账号没有昵称（解密其 contact.db 需要该账号登录时的密钥），下拉仍显示 wxid；登录/监控过一次后即记住。

## 客户机反馈第三轮：切换到未登录账号后仍显示上一账号数据（未 commit）

用户真机操作：把监控账号切到当前未登录的 kun（右上角已正确提示「当前登录的微信不是所选监控账号」），但「设置 → 监控对象」左栏仍显示原账号（安佳胤）的群/好友，20 个已选监控对象也还在。并提问：商机列表等是否应跟随监控账号同步切换。

### 根因（已在用户机器数据上确认）

1. **解密缓存/密钥只按库相对路径命名**：workdir 一直是共享的 `D:\wechatauto_cache`，`keys.json` / `.pages` / `.stamp` 无账号维度。切到 kun 时 `_open()` 命中安佳胤的解密缓存；且 `_load_or_extract_keys` 校验失败的旧密钥仍留在 `_keys`，继续解密/回退到旧缓存 → 联系人/群列表就是安佳胤的。
2. **未登录账号没有快速失败**：所选账号目录仍在（历史登录留下 db_storage），代码继续构造 WeChatDB，扫描进程内存 ~110 秒且注定失败，期间/之后仍可能读到旧缓存。
3. **前端候选列表 queryKey 不含账号**：切换后（尤其切换失败时 `onSuccess` 不执行）旧候选一直留在 react-query 缓存里。
4. **监控对象/商机/分析日志是全局表**：`monitor_targets.username UNIQUE`、`opportunities` 无账号列，切号后已选对象与历史商机天然还是原账号的（设计层面，非缓存 bug）。

### 已实施

- **缓存/密钥按账号隔离**（`wechat_service._open_listener_locked`）：workdir 改为 `<缓存根>/<账号>`；`_adopt_legacy_keys(target, base)` 首次升级时从共享根/旧 %TEMP% 迁移 `keys.json`/`image_keys.json`（优先级：共享根 > 同名账号目录 > 最新其它账号；已有目标文件绝不覆盖）。
- **旧密钥清理**（`wechatauto/db.py::_load_or_extract_keys`）：页 1 HMAC 明确失败且内存中存在的密钥 → 从 `_keys` 移除并回写 keys.json；源库暂时读不到不判失效（避免误删可用密钥）。
- **未登录账号快速失败**（`_account_instance_absent`）：全部运行中微信主实例的 `open_files()` 句柄都明确指向别的账号 → 直接降级「所选监控账号当前未登录」，不构造 WeChatDB；句柄未知/无微信不拦（宁可不拦不误伤）。失败分支同时清空账号相关内存缓存。
- **句柄判定抽成模块函数** `wechatauto.db.pid_account_match(pid, db_dir, account, account_dir)`，`WeChatDB._pid_account_match` 改为委托（服务层无 WeChatDB 实例也能用同一证据）。
- **缓存目录信息**：`dir_usage` 递归统计（账号子目录计入）；`cache_dir_info.active` 认可「配置目录的子目录就是当前 workdir」，避免设置页误报未生效。
- **前端**：监控对象候选与群总结候选 queryKey 带上当前账号（`status.wechat.account.account`）；切号 mutation 在 `onSettled`（成功/失败都）失效 targets/candidates/sessions/summary 系列/image-key，失败切换也会刷新界面（后端会把所选账号落库并降级）。
- **测试**：新增按账号子目录/自动解析账号/未登录快速失败/句柄未知不拦/账号目录不存在不回退、密钥清理与「源库不可读不误删」、迁移优先级、递归占用、`pid_account_match` 委托、`_account_instance_absent` 四场景。

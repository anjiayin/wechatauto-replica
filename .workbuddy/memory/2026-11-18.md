## 架构评审：两地址能否靠自动升级修改（架构师评审，仅分析未改代码）
- **结论：当前两个地址都不能靠自动升级改。** 关键事实已 Grep 核验。
- 授权地址 `license.server_url`：优先级 `KEFU_LICENSE_SERVER` env > data 层 DB settings > 内置常量；DB 值由 bundle 根 `delivery_seed.json` 经 `db.py::_apply_delivery_seed()`（按文件原始字节 sha256 幂等，标记 `runtime.delivery_seed_applied`）注入。`build_release.py` 增量包只含 `kefu-system`/`wechatauto`，`update_service.apply()` 只解压 app/<版本> + 切 junction + 写 current.json，不写 seed 也不写 DB → seed 未变则 hash 命中跳过，地址不变。
- 升级地址：唯一来源是 bundle 根 `update_config.json` → `launcher._child_env()` 注入 `KEFU_UPDATE_MANIFEST_URL`（直接赋值、覆盖继承 env）→ `update_service.py:31` / `packaging/updater.py:51` 在 import 时固化。**manifest 里的 `manifest_url` 字段是死字段**（`update_core.py` 无 `consume()`、全文件无 `manifest_url` 字样，`fetch_manifest` 只用传入 url）；apply() 不回写 update_config.json。发布工具提示仍是「手工复制 update_config.json + 重打安装包」。
- 鸡生蛋风险：升级地址一旦失效，无任何代码路径写新地址 → 永久失联，只能人工改 bundle 根文件或重装。授权地址失效则靠 `license.state.json`（data 层，不覆盖）的 `last_ok_at` 宽限 7 天，但升级也救不了地址本身。
- 若要支持（最小改造）：manifest 加 `delivery` 段（license_server_url / manifest_url；整包已被 Ed25519 签名，自动获得验签保护）→ `update_core` 加 `extract_delivery_config()` 纯函数 + http(s) 校验 → `update_service.apply()` 在切 junction 成功后写 DB `license.server_url` + 原子写 bundle 根 `update_config.json`（失败可重试标记）→ `packaging/updater.py` 同步（两个写入点需一致）→ 新增来源标记防 seed hash 变化把地址冲回。首次安装包内置 update_config.json 必须保留作 bootstrap（建议改回退地址列表）；首个支持版本须靠当前有效旧地址推送；授权服务器若换密钥对须同版本更新 `license.py::PUBLIC_KEYS`。
- 现状可手工改地址：改 DB settings / 设 `KEFU_LICENSE_SERVER` env / 重装带新 seed 的安装包；改升级地址则改 bundle 根 update_config.json 或重装。应用内无改地址界面。

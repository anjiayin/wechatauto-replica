## 1.4.2 缓存晋升 WinError 5（A+C 修复，未提交）

**症状**（用户截图，打包版 1.4.2 运行日志 10:40:00 / 10:40:30；日志实体在
`WeChatKefu\data\launcher.log`，`kefu.log` 与 `wechatauto_logs` 里都没有这些行）：
`contact__contact.db 晋升失败原因: PermissionError: [WinError 5] 拒绝访问 …（重试 60 次仍未释放）`
+ `缓存重建完成但晋升失败（正式缓存被占用？），耗时 12.5s，下轮重试`。
11:05–11:06 复查仍在继续（累计 18 条，单轮耗时 12.8~19.0s，穿插着 message_8 的成功重建），
**不是一次性的升级抖动**：contact 是每轮轮询都要读的热分片。

**根因（已用真机语义实测证实，不是推测）**：临时缓存 `os.replace` 到正式缓存时，
**本进程自己**的只读连接正占着目标文件。SQLite 在 Windows 打开库文件不带
`FILE_SHARE_DELETE`，**一个连接就足以让 replace 永久失败**：

```
leases: {'contact__contact.db': 1}
RESULT: replace BLOCKED as theorized -> PermissionError [WinError 5]
promote ok=True cost=0.61s        # 修复后：释放登记在案的连接，第 4 次尝试换上新缓存
now content: [('NEW',)]
sqlite version: 3.45.3
```

旧实现只能「被动等对方关连接」，12s（60×0.2s）窗口在轮询高峰期一次空档都等不到
（1Hz 采样：pid 14060 对 contact 的 `.db/-shm/-wal` 连续握住 ≥7s）。
集中出现在 10:37:27 升级到 1.4.2 之后：1.4.2 是第一个把解密缓存落在**按账号子目录**
`data\wechat_cache\wxid_…_ac0e\` 的版本，那是该目录的首轮补建（重建 9~12s）+ 监听高频读库。
10:41:18 已自行晋升成功（`/api/status` 里 `last_error=''`、`fail_streak=0`）——属可自愈的临时争用，
代价是那两轮白烧 12.5s CPU/IO + 缓存停在旧版本，**不误发、不损坏数据**。

**改动**（`wechatauto/db.py`）：
- A 主动制造空档：模块级 `_RO_LEASES` 登记表 + `_RoCacheConn`（`close()` 自摘除）。
  `_connect_ro` 登记并在晋升期间让路；`_promote_cache` 先被动试 `PROMOTE_PASSIVE_ATTEMPTS=3`
  次，等不到就打 `_PROMOTING_PATHS` 暂停标记（新读连接最多让路 1s）并 `_release_ro_leases(dst)`，
  主动阶段 `PROMOTE_ACTIVE_ATTEMPTS=10` 后收手。**sqlite3.Connection 不支持弱引用**
  （实测 `cannot create weak reference`），所以泄漏的连接靠 `MAX_RO_LEASES_PER_PATH=32` 上限回收。
  **`_connect_ro` 必须带 `check_same_thread=False`**：默认 True 时跨线程 `close()` 抛
  ProgrammingError，重建线程关不掉轮询线程的连接，整套释放逻辑变成空转（写第一版时踩过，
  实测 0/8 成功、每次仍白烧 12.1s 才发现）。关不掉的连接留在名册里，不静默摘除。
- C 退避：`_record_promote_fail`/`_promote_backoff_left`，`_kick_rebuild` 在
  `PROMOTE_FAIL_BACKOFF_SEC=180s` 内不再重建（沿用旧缓存），`_record_cache_ok` 解除；
  晋升窗口从最长 12s 缩到 ~2.6s（不再长时间占着 `MAX_CONCURRENT_REBUILDS` 配额）。
- 副作用兜底：被强制关闭的在跑查询抛 `ProgrammingError: Cannot operate on a closed database`，
  `_run_msg_query` 新增 `_is_released_mid_query` 分支 → 重开连接重试一次，**不走**「库损坏→失效重建」。
- 顺带修掉同区域两个既有缺陷：① `get_self_info` 拿到连接从不 close（正是长期句柄来源）；
  ② WAL 兜底分支 `_promote_cache` 返回值被忽略却照写 stamp → 缓存停在旧数据却被记为已追平（静默陈旧）。
- 可观测性：`cache_status()` 增加 `promote_backoff` 字段（前端未改，`/api/status` 可直接看）。

**A/B 压力实测**（`/d/tmp/stress_hold.py`，3 个线程长期持有连接、句柄几乎不空，8 次晋升）：

```

被动3 + 主动释放10 (修复后)   ok=8/8  avg=0.23s  max=0.61s   final=NEW7
                             读查询被打断 6/603 ≈ 1%（重开即可），暂停标记与名册均无泄漏
```

另两轮轻量压力（`stress_promote.py` / `stress_promote2.py`，读-放-读交替）：12/12 成功、
0 次打断，说明常态轮询下几乎不会打断任何查询。

**测试**（`kefu-system/tests/test_promote_release.py`，17 条）：登记表开/关摘除、双 close 幂等、
上限回收泄漏；真机 Windows 用例证明「不释放必然 WinError 5、释放后换得上」；被动阶段不动别人
的连接、主动阶段才释放、失败后清临时文件保留旧缓存；暂停让路与 1s 超时上限；**跨线程确实关得掉

## 1.4.3 现场回归：`_promote_fail_at` 缺失导致缓存重建全停（已修，未提交）

**用户反馈**：升级到 1.4.3 后运行日志出现
`ERROR app.wechat_service 读取解密缓存健康度失败（按空列表处理）` +
`AttributeError: 'WeChatDB' object has no attribute '_promote_fail_at'`，
随后 `message\message_8.db 解密缓存已 121 秒未成功更新（源库仍在变化）…连续失败 0 次，
最后错误: 无`；并且**手工发了一条提示消息没有被抓到**。

**根因（我上一批 A+C 改动引入）**：`WeChatDB.__init__` 与 `_ensure_cache_state()` 各有一份
缓存健康度字段清单，且 `__init__` 结尾把 `_cache_state_ready = True` 直接置上；
新字段 `_promote_fail_at` 只加进了 `_ensure_cache_state()` 的 `hasattr` 惰性分支
（`db.py:1626`），真实实例因此永远没有它。测试之所以全绿：本文件所有替身都用
`object.__new__(WeChatDB)` 构造，恰好绕过 `__init__`。

**影响链（两条现象同一个根因）**：
1. `cache_status()` → `set(self._promote_fail_at)` 抛 AttributeError → `/api/status`
   缓存健康度按空列表处理（前端面板空白）；
2. `_kick_rebuild()` **第一行**就是 `self._promote_backoff_left(rel)` → 同样抛错 →
   沿 `_open()`（`db.py:1884`）冒到 poller 的 `except Exception: continue`
   （`db.py:4191`）被静默吞掉：既没有异常日志，也再没启动过一次后台重建。

**实测证据**（`WeChatKefu\data\launcher.log` + 缓存目录 mtime）：
最后一次成功晋升 message_8 = **11:43:27**、session = 11:43:37、contact = 11:38:52；
1.4.3 的 poll #1 从 11:44:18 开始，此后**整份日志 0 条「缓存重建完成/晋升」记录**，
54 条 traceback 全部来自 `cache_status`。也就是说用户发消息时轮询读的是 12 分钟前的
旧缓存 —— 消息在源库里，不在缓存里，所以「没抓到」，与 WinError 5、与双开无关。

**修复**：`__init__` 不再自己铺这些字典，改为调用 `self._ensure_cache_state()`
（`db.py:885`），字段清单只剩一处出处，这类「加字段忘改另一处」的结构问题不会再犯。
新增 `TestRealInitCacheState` 两条用例：走真实 `__init__`（只替换账号探测/扫库/取密钥），
一条断言 `_ensure_cache_state()` 铺出的字段集合 ⊆ 实例字段集合（未来加字段自动纳入），
一条跑 `cache_status()/_record_promote_fail()/_promote_backoff_left()/_record_cache_ok()/
_kick_rebuild()` 全链路不得抛异常且能正常起线程。
**A/B 验证**：把 `__init__` 临时改回旧写法，两条用例立即复现同一条
`AttributeError: 'WeChatDB' object has no attribute '_promote_fail_at'`；恢复后转绿。

**测试**：`test_promote_release + test_bugfix_124_convergence + tests/test_db_cache` 47 passed；
**全量：1944 passed, 10 skipped, 2 xfailed, exit 0（705.17s）**（比上一批多出的 2 条即本次新增）。

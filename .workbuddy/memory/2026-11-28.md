## 修复：「@发送人 + 引用最新一条」偶发 1.3s 快速失败（未 commit）

**现象**（用户截图，打包版 1.4.1 真机）：企业微信群「微闪连企业微信测试」的商机，勾选 @发送人 + 引用最新一条 → 微信窗口正常打开、会话也定位到了，但 @ 与引用动作没执行，提示「发送失败：@ 成员/引用操作未完成，已取消发送（组件初始化 0.0s · 前置窗口 2.0s · 打开会话 4.9s · 输入发送 1.3s · 合计 8.2s）」。8 分钟后同会话同参数再测 → 成功（输入发送 6.6s）。

**归属判定**：失败发生在**打包实例**而非开发后端——两条日志库的商机编号不同（打包 #76 / 开发 #288），发送记录只出现在 `WeChatKefu\app\1.4.1\kefu-system\wechatauto_logs\app_20261126.log` 与 `WeChatKefu\data\kefu.log`。

**根因（用耗时反推 + 代码核对）**：
- 引用分支固定耗时下限 ≈1.8s（`_right_click_latest_row` 右键后 `sleep(1.0)` + 菜单点击 0.3s + 建卡片 0.5s），再加 @ 的 0.45s；实测只花 1.3s ⇒ 根本没进到右键，是在取消息列表时就返回 None。
- `_message_list()` 是**一次性遍历、零重试**（对比 `voice_call` 有 6 次重试）；窗口刚从托盘/最小化恢复或 UIA 树刚重绑时控件树未物化 → 读空 → `_prepare_quote` 返回 None → `at_members` False → guia 侧 fail-closed 报「@ 成员/引用操作未完成」。
- 该读空分支原先**不打日志**，与打包日志 09:42 段无任何 debug 行吻合。
- 旁证（同窗口期）：09:47:52 一次「输入发送 46.9s」极端卡顿、09:49:38 托盘单击恢复、09:50:08 最小化自动恢复 + 「清空 UIA/会话缓存并重新绑定」。
- 不是回归：11-15 那次（`affb7bd`）修的是「引用被静默丢弃却报成功」与「OCR 兜底白等 20~30s」，改成现在的 fail-closed；本次踩的是它上游一步的读空缺口，1.4.1 里带的就是同一份逻辑。

**修复**（`wechatauto/uia_driver.py`）：
- 抽出 `_latest_message_row()`：取可视区 bottom 最大的 `mmui::Chat*` 行，跳过 ChatItemView 时间行/系统行与 <40px 未布局行（规则原样搬，行为不变）。
- `_right_click_latest_row()` 对列表读取重试 `_LATEST_ROW_ATTEMPTS=4` 次、间隔 `_LATEST_ROW_WAIT=0.4s`（最多 +1.6s），读到即右键；仍读不到照旧返回 None —— **fail-closed 不变，不降级成「不引用直接发」**。
- 补两条 debug 日志区分两种失败：「消息列表连续 4 次读空」与「已右键但两次都没找到『引用』菜单项」。

**测试**（`kefu-system/tests/test_quote_locating.py` 新增 `TestLatestRowRetry` 3 条）：一直读空→重试 4 次且绝不右键；第 2 次读到就立刻右键且不再多读；抽出后筛选规则不变。

# 技术方案：多微信并发监控 + 标准版/专业版授权

> 文档版本：v1（2026-11-28），状态：**待评审，未进入开发**。
> 范围：`kefu-system`（客服后端 + 前端）、`license-server`（授权服务）、`wechatauto`（底层微信库，仅少量适配）。
> 前置事实基线：当前 main（`2e23d31`，1.4.4）。1.3~1.4 已落地「单账号监控 + 账号切换 + 账号↔PID 绑定 fail-closed + 业务数据按 account 隔离」，本方案是在此之上把「单账号」升级为「多账号并行」，**不是从零做多账号**。

---

## 1. 背景与目标

### 1.1 现状

当前系统任意时刻只监控**一个**微信账号：

- 通过「设置 → 数据与账单 → 监控微信账号」选择/切换账号，切换即停旧 Listener、开新 Listener（`kefu-system/app/wechat_service.py:544` `switch_account`）。
- 发送按「当前账号 ↔ Weixin.exe PID」绑定定向操作，绑定不确定时 fail-closed 暂停回复（`kefu-system/app/sender.py:356`、`:842`）。
- 业务数据（监控对象/商机/分析日志/定时总结）已带 `account` 列，接口默认只查当前账号，`all_accounts=1` 看全部。
- 授权只区分「已激活/未激活/过期/吊销」，`edition` 字段仅展示，不参与任何功能控制（`kefu-system/docs/授权服务接口文档.md` 明确「客户端目前不解析」「features 预留不校验」）。

双开客户机的真实诉求：两个微信同时在线、同时收消息、分别按各自配置监控与回复，而不是来回切换。

### 1.2 目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | 多微信并行监控 | 同一台机器上多个已登录 Weixin.exe 实例，各自独立监听消息、独立监控对象集合、互不影响 |
| G2 | 回复按账号路由 | 每条回复任务绑定来源账号，只操作该账号的微信窗口；保留现有 fail-closed 语义 |
| G3 | 配置按账号区分 | 监控对象、分析/回复策略、定时总结等支持「全局默认 + 账号覆盖」 |
| G4 | 数据按账号区分 | 所有与账号相关的数据（含 watermark、语音/图片缓存、群名片、用量）可按账号过滤与统计 |
| G5 | 授权分版本 | 标准版 = 现状单账号；专业版 = 多账号并行；由授权服务端签发、客户端强制门禁，升级/降级随心跳生效 |

### 1.3 非目标（本期不做）

- 不做微信多开器、不注入/修改微信进程、不做 Hook 消息收取（仍走现有「DB 解密读 + UIA 写」混合驱动）。
- 不做多台机器/多设备共享同一授权，不做账号云端同步。
- 不做多账号 UIA **并行**发送（Windows 桌面焦点是全局资源，见 §4.3，发送仍然串行，只是按账号路由）。
- 不重写 AI 分析管线、不改商机判定逻辑、不改计费单价模型（只加账号维度）。
- 不做 wechatauto 库的多账号 API 重设计（库本身已支持按 account 构造实例，见 §3.4）。

## 2. 术语与标识

| 术语 | 含义 | 示例 |
|---|---|---|
| `account` | 微信账号目录名（`db_storage` 上级目录），系统内账号主键 | `wxid_abc123_x1y2` |
| `wxid` | 去掉目录名 4 位哈希后缀的微信号 | `wxid_abc123` |
| 实例 / PID | 一个运行中的 Weixin.exe 主进程（已剔除子进程） | `enumerate_weixin_pids()` |
| 绑定（binding） | account ↔ PID 的确认关系，`mapped=false` 时禁止自动回复 | `account_binding()` |
| 监控集合 | 本机被启用并行监控的账号列表（专业版 >1，标准版恒 =1） | 新设置键 |
| 查看作用域 | 前端当前筛选数据的账号（单个 / 全部），**不等于**监控集合 | 新 API 参数 |
| 账号运行时 | 一个账号的 WeChatDB + Listener + 缓存 + 绑定状态（新对象） | `AccountRuntime` |

## 3. 现状架构与改造点清单

### 3.1 运行时单例（核心改造对象）

`main.py:189-263` 启动时装配：`Database / Notifier / Aggregator / Pipeline / Sender / WeChatService / SummaryScheduler / LicenseClient`，授权通过后 `_start_runtime()` 才启动。

| 组件 | 现状（文件:行） | 多账号问题 | 处置 |
|---|---|---|---|
| `WeChatService` | 单例，持有唯一 `_wxdb`/`_listener`/`_listener_lock`（`wechat_service.py:136-141`） | 只能有一个监听 | **拆分**：每账号 `AccountRuntime` + 全局 `AccountManager` |
| 账号缓存 | 显示名/alias/企业联系人/联系人列表/群成员/会话时间/self_wxid/媒体下载器/绑定缓存全部在单例上（`wechat_service.py:151-195`） | 切号靠 `_reset_account_caches()` 全清（`:589`），并行会互相污染 | 缓存下沉到 `AccountRuntime` |
| 消息回调 `_on_message` | 用 `self._account_for_queries()` 取「当前账号」盖章（`:1130`） | 并行时「当前账号」无意义 | 回调闭包绑定账号（§4.4） |
| 共享队列 | 语音补转写、图片识别 worker、图片补识别队列挂在 WeChatService 上（`:206-230`） | 多账号共用可以，但任务必须带 account | 保留共享，任务带账号，落库带账号 |
| `Sender` | 单发送线程 + 单 `_gui` + 单 `_gui_lock`（`sender.py:117-137`） | 单 GUI 只绑一个账号 | 保留单线程，GUI 改为按账号缓存（§4.3） |
| `Aggregator` | 缓冲键已含 account（`aggregator.py:137-138`），`AnalysisUnit.account` 已透传 | 基本就绪 | 仅确认 flush/落库全链路账号不丢 |
| `Pipeline` | 单队列多 worker，账号随单元透传 | 共享即可 | 增加账号级公平性/限流（可选，§9 风险） |
| `SummaryScheduler` | 只跑「当前账号」配置（`summary.py:701-750`），当日去重键不含账号 | 并行时只会有一个账号出总结 | 遍历监控集合，去重键加账号 |
| `Notifier` | 全局 WS 广播 + 全局未读 id 集合；`/api/status` 按当前账号过滤未读（`router_system.py:144-145`） | 前端无法区分事件来源账号 | 事件负载带 account + 前端按作用域过滤 |

### 3.3 API / 前端现状

- 账号接口：`GET /api/wechat/accounts`、`POST /api/wechat/account`（`router_system.py:579-630`），切换返回新账号的 `monitored_count/monitor_quota`。
- `/api/status`：`wechat.account`（单账号绑定信息）、`monitored_count`、`monitor_quota`、`degraded_reason` 全部是「当前账号」单值语义（`router_system.py:115-157`）。
- 列表接口：`all_accounts=1` 二值语义（`router_targets.py:70-90`、`router_opportunities.py:155-172`、`router_analysis.py:157-186`），无法表达「只看账号 B」。
- 前端：`App.tsx` 顶栏单账号标识与「未确认实例」红色横幅（`App.tsx:444-498`）；设置页单账号选择；监控对象/商机页「显示全部账号」开关；授权页 `LicensePanel.tsx` 展示 edition。

### 3.4 wechatauto 库的多实例可行性（已核实）

- `WeChatDB(db_dir, workdir, account, ...)`（`wechatauto/db.py:852-886`）：账号、缓存目录、密钥、分片锁、重建锁**全部是实例字段**，没有模块级共享状态；缓存目录已按 `<缓存根>/<账号>` 隔离（`wechat_service.py:675-692`）。→ **可以多实例共存**。
- `Listener(db, interval, watermark)`（`wechatauto/db.py:4012-4111`）：独立轮询线程 + 每会话串行 worker，绑定单个 WeChatDB。→ 每账号一个 Listener 即可。
- 账号↔PID：`enumerate_weixin_pids()`、`find_account_pid()`、模块级 `pid_account_match()`（句柄证据）已就绪。
- `WeChatGUI(pid=)` 定向、绑定实例禁 `wake()` 已就绪（1.3 双开修复）。
- 需要注意的库级成本：WeChatDB 构造含密钥提取/内存扫描，单账号冷启动可达十几秒~110 秒；多账号启动必须**串行 + 后台线程 + 单账号失败不拖垮其它账号**（§4.5）。

## 4. 总体设计

### 4.1 架构：账号运行时注册表 + 全局共享服务

```
                 ┌────────────────────────────────────────────┐
                 │              FastAPI / 前端                 │
                 │   查看作用域: account=<dir> | all           │
                 └───────────────┬────────────────────────────┘
                                 │
        ┌────────────────────────┼─────────────────────────┐
        │                        │                         │
┌───────▼────────┐     ┌─────────▼─────────┐     ┌─────────▼─────────┐
│ AccountManager │     │  Sender（全局单例） │     │ LicenseClient     │
│ (监控集合/启停/  │     │  单队列单线程      │     │ + Capabilities    │
│  降级/看门狗)    │     │  GUI: dict[账号]   │     │ (版本/账号数门禁) │
└───┬────────┬───┘     │  _gui_lock 全局    │     └───────────────────┘
    │        │         └─────────▲──────────┘
┌───▼──┐  ┌──▼───┐               │ SendTask.account（已有）
│Runtime│  │Runtime│  … N 个      │
│账号A  │  │账号B │               │
│WeChatDB│ │WeChatDB│             │
│Listener│ │Listener│             │
│缓存/绑定│ │缓存/绑定│            │
└───┬──┘  └──┬───┘               │
    └────────┴── msg(_account) ──▼──► Aggregator(键含account) ─► Pipeline(共享)
                                        │                        │
                                        └──── 落库全部带 account ─┘
```

**决策 D1（推荐）**：引入 `AccountRuntime`（每账号）与 `AccountManager`（全局），`WeChatService` 退化为对外的门面/兼容层，逐步把方法委托给 Manager。这样可以保留现有 API 注入形状（`deps.get_wechat_service()`），测试替身改造成本最低。
备选：直接新建 `MultiWeChatService` 替换旧类。改动更干净，但对 1900+ 既有测试与大量 `getattr` 兼容分支冲击大，不推荐一次性替换。

**决策 D2**：共享 `Aggregator / Pipeline / Sender / ASR / 视觉 worker / Notifier`，不随账号倍增。账号间天然隔离已由「消息带 account + 缓冲键含 account + 落库带 account」保证。
例外：与微信实例强绑定的东西（WeChatDB、Listener、媒体下载器、图片密钥、联系人/群缓存、self_wxid、GUI）必须按账号独立。

### 4.2 监控集合与标准版约束

- 新设置键 `runtime.wechat_accounts`：JSON 数组，持久化监控集合（有序，首个为「主账号」）。
- 旧键 `runtime.wechat_account`（单值，`config.py:241`）保留做迁移来源：升级后若新键为空且旧键非空 → 迁移为 `[旧值]`；旧键此后仅作兼容写镜像（主账号），避免旧逻辑/旧测试读空。
- **标准版**：集合长度恒 ≤1，UI 与 API 表现为现有「单账号选择/切换」，行为与 1.4.x 完全一致。
- **专业版**：集合长度 ≤ `max_accounts`（授权下发，建议默认 3，上限见 §8 待拍板）；支持添加/移除/停用某个账号，不影响其它账号运行。
- 「自动选择最近活跃账号」模式（旧键为空）在新模型下等价于「集合为空 → 启动时自动选 1 个」，标准版/专业版都保留该兜底；专业版自动模式也只自动选 1 个，多账号必须用户显式添加（避免误监控不想监控的账号）。

### 4.3 发送：监控并行、回复串行（关键决策 D3）

Windows UIA 操作依赖窗口激活/焦点/模拟输入，两个微信窗口**不能真正并行**执行「打开会话→输入→@→引用→发送」。因此：

- 保留**全局唯一发送线程 + 全局 `_gui_lock`**（跳转微信 API 也继续共用这把锁）。
- `SendTask.account` 已有（`sender.py:114`），语义从「与当前账号比对，不符则取消」改为「**路由键**」：
  1. 按 task.account 找到对应 `AccountRuntime` 的 binding（账号→PID）；
  2. binding 未确认 → 该任务失败并给出该账号原因（fail-closed），**不影响其它账号任务**；
  3. GUI 缓存改为 `dict[account] → WeChatGUI`，实例/PID 变化只重建该账号的 GUI（现有 `_ensure_gui` 逻辑按账号下沉）；
  4. 发送前不再做「切换账号即取消」，因为多账号下旧任务依然合法；仅当该账号已被移出监控集合时才取消。
- 排队与公平：单队列 FIFO + 每账号最大在途数（如每账号最多 3 条待发送，超出排队或提示），防止一个账号的积压饿死另一个账号。是否需要轮转调度见 §8 开放问题。
- 结果：`professional` 的价值是「多路同时收、集中排队回」，UI 必须在发送按钮旁说明「多微信回复为串行发送，可能排队」。
- 手动确认模式（只填输入框不点发送）在多账号下风险更高：必须在填完后**不切换窗口**，并在任务间清理输入框残留；若用户手动操作了另一个微信，任务按现有「发送前校验会话」兜底失败。

### 4.4 消息链路：账号在源头盖章（D4）

- 每个 `AccountRuntime` 创建 Listener 时注册闭包回调 `lambda msg, l: self._on_message_for(account, msg)`，账号在**入口处**写入 `msg["_account"]`，取代 `_on_message` 内读取全局当前账号（`wechat_service.py:1130`）。
- 该回调内所有依赖「当前账号」的查询（monitor_since 过滤、target 查询、self_wxid 过滤、群名片学习、语音/图片任务、显示名解析）全部改为显式使用闭包账号。
- Aggregator/Pipeline 无需结构改动；落库前增加断言：account 为空时按「未归属」落库并打 warning（便于发现漏盖章路径），不阻断。

### 4.5 生命周期与降级（D5）

- 启动：授权通过 → 读监控集合 → 后台线程**逐个串行**启动 AccountRuntime（密钥提取是 CPU/IO 密集且可能读进程内存，禁止并发扫描）；单账号失败只标记该账号降级。
- 单账号状态机：`starting / running / degraded(reason) / stopped`，与现有全局 `_available/_reason` 对应但按账号独立。
- 看门狗：周期性（建议 30s）检查每个账号：Listener 线程存活、PID 仍存在且仍持有该账号句柄（复用 `pid_account_match`）、窗口可绑定。账号微信退出 → 该账号转 degraded，其它账号不受影响；重新检测到可恢复时提供「重新连接」（自动恢复是否默认开启见 §8）。
- 停止：逆序停所有 Runtime（每个都要刷回自己的 watermark），共享服务最后停；`stop()` 总耗时要控制在现有退出流程可接受范围（每账号 join 5s 上限，并行等待）。
- 授权运行时变化（心跳后 pro→standard 或到期）：立即停止「多余账号」的 Listener 与发送能力，**数据一律不删**（沿用授权锁定不动数据的原则）。

### 4.6 配置分层：全局默认 + 账号覆盖（D6）

新键规范：`account.<accountDir>.<原设置键>`，读取顺序 `账号覆盖 → 全局键 → 代码默认值`；提供 `get_setting_scoped(db, account, key)` 统一入口，禁止业务代码各自拼接。

| 配置 | 作用域建议 | 理由 |
|---|---|---|
| 监控对象集合 | 账号（已实现） | — |
| `monitor.max_targets` | **每账号配额**（授权给默认值，允许账号覆盖调低） | 多账号下总量语义见 §8 |

## 7. 授权方案（标准版 / 专业版）

### 7.1 能力模型

复用现有签名 payload，**不改变签名结构**，只约定字段语义：

```json
{
  "edition": "standard | pro | trial",
  "features": ["monitor", "reply", "ai", "multi_account"],
  "max_accounts": 3
}
```

- `multi_account` 出现在 features 中 → 允许多账号；`max_accounts` 为可选正整数，缺省专业版默认 3（常量），标准版恒为 1。
- `trial` 的产品归属（等同 standard 还是 pro、是否限账号数）见 §8 待拍板；未拍板前按 standard 处理（fail-closed，不多给能力）。
- 不新增 `max_accounts` 也可以跑通（features 唯一决定 + 常量上限）；加字段的好处是同一 pro 版可卖不同账号档位。**建议加**，服务端只需在 `license` 表加一列并纳入 payload（旧客户端会忽略未知字段，验签不受影响，因为签名是对整个 payload 做的，客户端验签用原文而非字段白名单）。

### 7.2 客户端（`license.py` + 守卫）

- `LicenseStatus` 增加 `features: list[str]`、`max_accounts: int`；新增 `capabilities()` 返回 `{multi_account, max_accounts}`：
  - 授权未启用（dev 测试模式）→ 视为 pro + 默认上限，但日志与横幅保持现有测试模式警示；
  - 已启用但证里没有 features（旧服务端签发的证）→ 按 `standard`（fail-closed），保证不会因为旧证缺字段而意外放开多账号；
  - 状态非 ok（过期/吊销/离线超期等）→ 现有全局拦截已锁业务接口，能力值不再重要。
- 门禁位置（不能只在前端隐藏）：
  1. 启动 `_start_runtime`：按 capabilities 裁剪监控集合；
  2. 账号管理 API：添加/启用第二个账号时校验；
  3. 心跳后能力变化：pro→standard 时保留主账号运行，其余账号停止并标记 `paused_by_license`；standard→pro 时提示用户手动启用（不自动拉齐，避免意外开始监控）。
- `license_guard` 现有「只锁接口不动数据」语义不变。

### 7.3 服务端（license-server）

- `schema.sql`：`license` 增加 `max_accounts INT NOT NULL DEFAULT 0`（0=按版本默认）；`license_code` 增加同名列，发码时可指定档位。
- `signing.build_payload`：features 数组 + 可选 `max_accounts`（>0 才输出，保持旧 payload 形状稳定）。
- 激活/续期：沿用「激活码决定 edition」；续期时同步 `max_accounts`；审计 `after` 记录版本变化（`standard→pro` 必须能在审计里查到）。
- 管理后台：
  - 发码页版本改为下拉（standard/pro/trial），默认 standard；选 pro 时显示账号数输入（默认 3）；
  - 许可证列表/详情显示版本与账号上限，支持筛选；
  - 新增「变更版本」操作（B18）：只改 edition/features/max_accounts，不动到期日；强制填写备注，写审计；下次心跳生效。
- 文档：更新 `kefu-system/docs/授权服务接口文档.md` 中「客户端不解析 edition/features」的契约描述。

### 7.4 升降级与兼容矩阵

| 场景 | 行为 |
|---|---|
| 新客户端 + 新服务端，pro 码 | 多账号可用，心跳改版本后 ≤5 分钟内生效（现有心跳循环） |
| 新客户端 + 旧服务端（无 max_accounts 列） | features 有多账号即可用，上限用客户端默认；旧服务端不能发 pro 码则只能 standard |
| 旧客户端（≤1.4.x）+ pro 证 | 旧客户端不解析 features，仍单账号运行，**不会出错也不会越权**；UI 提示升级（依赖新服务端/新文档说明，旧客户端无此提示属正常） |
| pro → standard（降级/换码） | 保留主账号，其余停监控；历史数据完整可查；集合持久化不变，重新升 pro 后可手动恢复 |
| 离线宽限期内 | 按本地证能力继续运行（与现行离线策略一致） |

## 9. 性能与资源预算（必须真机实测后才定稿上限）

单账号现状基线（来自既有实测记录）：WeChatDB 冷启动密钥提取十几秒级、媒体下载器首次约 13s、解密缓存单账号可达数百 MB、Listener 每会话一条 worker 线程、UIA 首次物化 15~30s。

多账号新增成本与对策：

| 资源 | 风险 | 对策 |
|---|---|---|
| CPU/IO | 多账号同时解密重建缓存、同时密钥扫描 | 启动串行；进程级扫描互斥；缓存预热状态展示 |
| 内存 | 每账号联系人/群缓存 + 解密连接 | 缓存加容量上限与 TTL；账号停用即释放 |
| 磁盘 | 缓存目录随账号数线性增长 | 缓存状态按账号展示大小；清理操作按账号执行 |
| 线程数 | N 账号 × M 会话 worker | 全机监控会话总上限（Q2）；Listener worker 可按需创建/空闲回收（如现状未回收则列为优化项） |
| AI 成本 | 多账号消息量翻倍，视觉/语音按次计费 | 账号级开关 + 每账号用量展示 + 预筛默认开启建议 |
| UIA 稳定性 | 多窗口热激活更频繁，历史上出现过「@/引用快速失败」「46.9s 卡顿」 | 保持串行；保留 1.4.2 的最新行重试；真机回归双开/三开场景 |
| 分析队列 | 单账号洪峰挤占另一账号 | 队列积压按账号指标；必要时每账号入队限流 |

## 10. 数据迁移方案（SQLite，全部幂等、可重复执行）

1. `watermarks`：重建表为 `PRIMARY KEY(account, username)`；存量行归属到「当前已打开账号」（复用 `backfill_account_scope` 的归属时机与幂等口径）；归属前保留空 account 行作为未归属，不与新账号混用。
2. `group_cards / voice_texts / image_analysis`：加 `account TEXT NOT NULL DEFAULT ''`，主键/唯一索引重建为含 account；读写 DAO 全部带 account；旧数据先按当时打开账号回填，无法归属的保留空串并按「全局共享只读」兜底（只读复用，不回写），避免重复烧钱重新识别。
3. `ai_usage / group_summaries`：加 account + 索引；旧数据回填；账单查询带作用域。
4. `settings`：写入 `runtime.wechat_accounts`（由旧单值迁移）；不删除任何旧键。
5. 所有迁移失败：记录日志并降级该账号，不阻断整个应用启动；迁移前自动备份业务库文件（沿用现有打包/升级的数据保护策略）。
6. 回滚：新版本不回写旧格式破坏性变更；若需回退到 1.4.x，旧版本忽略新列/新键即可（SQLite 加列天然向后兼容；`watermarks` 主键变化需保留旧表 `watermarks_legacy` 备份以便回退）。

- 数据迁移：1.4.x 旧库升级（含存量 watermark/语音/图片缓存），重复执行幂等；回滚备份存在。
- 配置分层：覆盖/跟随全局/非法键拒绝；配额按账号与总量。
- 授权：payload 含/不含 features 与 max_accounts 的解析；旧证 fail-closed；pro↔standard 心跳切换运行时行为；`edition_required/account_limit_exceeded`；dev 模式。
- 兼容：旧参数 `all_accounts=1`、旧 `POST /api/wechat/account`、旧 status 字段的契约测试全部保留。

### 11.2 真机验证矩阵（需用户授权后执行）

| 场景 | 步骤要点 | 通过标准 |
|---|---|---|
| 标准版双开 | 双开两个微信，尝试添加第二账号 | 被拒绝并出现升级引导；单账号监控/回复与 1.4.x 一致 |
| 专业版双开并行 | 两账号各配监控群，同时发消息 | 两边都产出商机且归属正确、日志/未读/计数按账号正确 |
| 回复路由 | 交替回复 A/B 商机，含 @+引用最新 | 只操作对应微信窗口；无串号；串行排队可见 |
| 降级隔离 | 退出 B 微信 / 让 B 绑定不可确认 | 仅 B 暂停，A 正常；恢复后可重连 |
| 升降级 | 后台 pro→standard→pro | 5 分钟内生效；多余账号停止；数据不丢；可恢复 |
| 重启恢复 | 多账号运行中重启服务/机器 | 集合持久化恢复；不回放历史消息（启动水位闸门仍生效） |
| 性能 | 双开高消息量 1 小时 | CPU/内存/磁盘/AI 成本在预算内；无 UI 冻结 |

## 12. 发布与回滚

- 版本号：客户端次版本升级（建议 1.5.0）；`license-server` 独立发版并**先于客户端上线**（先发 pro 码能力，再发客户端）。
- 数据库：MySQL 先执行加列迁移（幂等）；客户端 SQLite 启动迁移（§10）。
- 打包/更新：沿用现有 `build_p1 / installer / release` 流程与增量更新机制，不在本方案改打包链路；注意增量包必须包含前端 dist 重建产物。
- 灰度：先内部 dev 模式双开验证 → 1 台专业版客户机灰度 → 再开放 pro 码销售。
- 回滚：客户端回退到 1.4.x（数据兼容见 §10.6）；服务端回滚只需停止发放 pro 码，已签发 pro 证可在后台变更版本降级。

## 14. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| UIA 串行导致多账号回复延迟被客户误解为「专业版不行」 | 高 | 文档与 UI 明示串行；提供排队状态；真机实测平均/尾延迟 |
| 账号↔PID 绑定在更多实例下误判 | 高 | 沿用句柄证据优先 + fail-closed；三开真机验证；误判时只停该账号 |
| 迁移把缓存/水位归错账号 | 中 | 幂等回填 + 备份 + 未归属只读兜底；升级后首启日志打印归属统计 |
| 多账号资源超预期（内存/磁盘/AI 费用） | 中 | Q1/Q2 上限 + 用量展示 + 灰度实测 |
| 授权绕过（改库/改配置开多账号） | 中 | 能力只来自签名证；运行时与 API 双重门禁；环境变量强制授权保持不变 |
| 既有 1900+ 测试与大量 `getattr` 兼容分支回归 | 中 | 门面兼容 + 契约测试保留；每个里程碑跑全量 pytest 与前端构建 |
| 标准版用户被新 UI 干扰 | 低 | 标准版界面保持现状，仅增加升级入口 |

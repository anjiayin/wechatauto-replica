# 电脑授权服务接口文档（授权服务器 ↔ 客户端）

> 面向对象：实现正式授权后台的开发同学。
> 客户端实现：`kefu-system/app/license.py`；参考实现（可直接跑）：`kefu-system/tools/mock_license_server.py`。
> 文档版本：v1（2026-11-13），对应客户端 `APP_VERSION`（唯一真源 `version.txt`，发版时以该文件为准）。

---

## 1. 这套授权是怎么工作的

一句话：**客户端算出一个本机机器码，拿激活码到服务器换一张「签了名的许可证」，
之后每次启动本地验签判断能不能用，定期联网确认一次。**

```
                    ┌──────────────────────────┐
   客户拿到软件      │  客户端（客户电脑）        │
   + 激活码    ───▶ │  1. 算机器码              │
                    │  2. POST /activate        │──┐
                    │     (机器码 + 激活码)      │  │
                    └──────────────────────────┘  │
                                                  ▼
                                     ┌────────────────────────┐
                                     │ 授权服务器              │
                                     │ 校验激活码 → 绑定机器码  │
                                     │ 用私钥签发许可证         │
                                     └────────────────────────┘
                                                  │
       ┌──────────────────────────┐               │
       │ 客户端本地保存 license.json │◀──────────────┘
       │ （payload + 签名）         │
       └──────────────────────────┘
                    │ 之后每次启动
                    ▼
       只用内置**公钥**验签 + 比对机器码 + 看 expires_at → 决定能否使用
```

关键点：**客户端只有公钥**。客户把程序目录翻遍也拿不到伪造许可证的能力，
这是选择非对称签名（Ed25519）而不是 HMAC 的唯一原因。

## 2. 三个概念

| 概念 | 说明 | 谁生成 |
|---|---|---|
| **机器码**（machine_code） | 本机唯一标识，形如 `BBCF-BCA8-F127-5747-05D8-46B3-E8D8-CAF0`（32 位大写十六进制，4 位一组）。Windows 上由注册表 `MachineGuid` + 系统盘卷序列号派生 | 客户端 |
| **激活码**（activation_code） | 售出后发给客户的字符串，形如 `KF-A9E4-BF83-259C-200E`。一码一机 | 授权后台（销售/客服在管理端生成） |
| **许可证**（license） | 服务器签名的 JSON 文档，含绑定机器码与到期日。客户端保存为 `data/license.json` | 授权后台签发 |

业务流程：

1. 客户装好软件，首次打开弹出激活窗口，显示本机**机器码**（可一键复制）。
2. 客户把机器码发给供应商；供应商在管理端生成激活码发回。
3. 客户输入激活码 → 客户端调 `POST /activate` → 拿到许可证 → 激活完成。
4. 之后每 6 小时（可配）静默调 `POST /heartbeat` 确认一次；
   服务器在这时可以顺带改期限、吊销授权（客户端会立即生效）。

**也可以更简单**：供应商拿到机器码后直接在管理端为它登记一个到期日（不生成
激活码），客户端调 `/activate` 时不带激活码也能成功——由后台的策略决定是否
强制激活码。参考实现走的是"必须激活码"，但保留了这个分支。

## 3. 客户端已实现的行为（后台必须知道的约定）

### 3.1 状态机

客户端本地判定，共 9 个状态：

| state | 含义 | 是否可用 |
|---|---|---|
| `disabled` | 未启用授权校验（开发/自用） | ✅ |
| `active` | 正常，近期联网确认过 | ✅ |
| `offline_grace` | 服务器连不上，但仍在宽限期内 | ✅ |
| `unlicensed` | 从未激活 | ❌ |
| `expired` | 超过许可证 `expires_at` | ❌ |
| `offline_expired` | 离线时间超过 `grace_days` | ❌ |
| `invalid` | 签名错 / 机器码不符 / 格式坏 | ❌ |
| `revoked` | 服务器明确吊销 | ❌ |
| `clock_rollback` | 系统时间被调早（比历史最大时间早 1 天以上） | ❌ |

不可用时：后端拦截所有 `/api/*` 业务接口（403），**只放行**
`/api/license/*`、`/api/status`、`/api/health`；微信抓取、AI 分析、消息发送
**不启动**。**数据库与缓存一律不动**——授权是商务问题，不能变成数据事故。

### 3.2 离线宽限

- 许可证里有 `grace_days`（默认 7）。客户端记 `last_ok_at`（最近一次成功联网确认的时间）。
- 服务器连不上：`now - last_ok_at <= grace_days` → `offline_grace`（可用，界面提示）；
  超过 → `offline_expired`（锁死，必须联网确认一次）。
- 所以**后台的 `/heartbeat` 必须在正常时稳定返回 200**，长期不可用会让客户离线超期。

### 3.3 时钟回拨检测

客户端记录历史最大时间戳 `max_seen_ts`。当前时间比它早 1 天以上 → 判定人为
调早时钟 → 锁死。后台不需要参与，但**不要**下发"很久以前"的 `issued_at`。

### 3.4 客户端请求头

```
Content-Type: application/json; charset=utf-8
User-Agent: kefu-system/1.0.0
```

超时 10 秒。**任何非 2xx 都会被视为一次失败**（不影响已激活状态，只推迟下次确认）。

## 4. 接口清单

客户端会调用的接口（**必须实现**）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/license/activate` | 激活（用激活码换许可证） |
| POST | `/api/v1/license/heartbeat` | 联网确认（续期/吊销生效） |
| GET | `/api/v1/license/query` | 查询某机器码的授权（可选，客服排查用） |

路径里的 `/api/v1` 是版本前缀，**必须保留**（客户端写死的）。若将来改版本，
用新路径并同步改客户端常量。

**不需要实现的能力（已确认下线）**：

- 客户机运行本系统必须联网（微信本身需要网络），因此**不做离线签发**：
  没有"按机器码预签发许可证"接口，也没有"许可证文件下载/导入"接口。
- 所有许可证一律由 `activate` 在线签发；**生成激活码时不需要机器码**，
  绑定发生在第一次激活时（服务端把 `used_by` 记为提交上来的机器码）。
- 管理端只需要"生成激活码 / 看列表 / 延期 / 吊销 / 恢复"五件事。

## 5. 接口详细契约

### 5.1 POST /api/v1/license/activate

**请求**

```json
{
  "machine_code": "BBCF-BCA8-F127-5747-05D8-46B3-E8D8-CAF0",
  "activation_code": "KF-A9E4-BF83-259C-200E",
  "app_version": "1.0.0",
  "os": "Windows 10"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| machine_code | string | ✅ | 客户端机器码。服务端需校验格式（32 位十六进制、可带 `-` 分组） |
| activation_code | string | 视策略 | 为空字符串表示"不带激活码"。若后台要求必须激活码，返回 `activation_required` |
| app_version | string | ❌ | 客户端版本，用于按版本下发不同策略 |
| os | string | ❌ | 系统描述，排查用 |

**成功响应（HTTP 200）**

```json
{
  "ok": true,
  "license": {
    "key_id": "prod-2026",
    "payload": {
      "license_id": "LIC-20261113-A1B2",
      "machine_code": "BBCF-BCA8-F127-5747-05D8-46B3-E8D8-CAF0",
      "customer": "某某汽配",
      "edition": "standard",
      "issued_at": "2026-11-13T21:02:53+08:00",
      "expires_at": "2027-11-13T21:02:53+08:00",
      "grace_days": 7,
      "features": ["monitor", "reply", "ai"]
    },
    "signature": "VGkDft9ofpxLJ+SqnjZGZHI3TAIZWJpbAnLlWVaqYFgNph+fz++secb4VInQh/j0cyeB2UU9hcIOy3alamnLCQ=="
  }
}
```

**幂等要求**：同一台机器重复激活**必须**成功并返回原来的许可证（客户重装
系统/重装软件会再次激活）。不要因为"机器码已存在"报错。

**吊销后的重新授权（正式后台必须实现这条规则）**

同一机器码存在**已吊销**记录时，按激活码本身的状态区分：

| 请求里的激活码 | 服务端行为 |
|---|---|
| 从未使用过的新码 | 视为供应商重新授权：签发**新** `license_id`，`revoked_at` 清空，旧记录保留作历史 |
| 该机器自己用过的旧码 | 返回 `revoked`，提示"需要供应商重新发一个激活码"——否则客户可以拿吊销前的码自助解封 |

两个容易踩的实现细节：

1. **一台机器同一时刻只能有一条生效记录**；按机器码查询时要取**最新**那条，
   否则旧吊销记录会让新许可证永远"看起来是吊销的"（模拟服务器踩过这个坑）。
2. 旧记录**不要删除**：审计与售后都要能查到"这台机器被吊销过、什么时候重新授权"。

**错误响应（HTTP 4xx）**

```json
{"error": {"code": "invalid_code", "message": "激活码不存在，请核对后重试"}}
```

客户端拿到 `message` 会直接展示给客户（所以请写**中文、可操作**的原因）。

### 5.2 POST /api/v1/license/heartbeat

**请求**

```json
{
  "machine_code": "BBCF-BCA8-F127-5747-05D8-46B3-E8D8-CAF0",
  "license_id": "LIC-20261113-A1B2",
  "app_version": "1.0.0"
}
```

`license_id` 可能为空（客户端本地许可证里没有时），此时**按机器码查**。

**成功响应（HTTP 200）**

```json
{
  "ok": true,
  "status": "active",
  "license_id": "LIC-20261113-A1B2",
  "expires_at": "2027-11-13T21:02:53+08:00",
  "license": { "key_id": "...", "payload": { ... }, "signature": "..." }
}
```

`license` 字段**建议每次都带上**：客户端收到后会验签并覆盖本地许可证，于是
"管理端延期"下一次心跳就生效，客户无需任何操作。不带也能用（只是期限不会刷新）。

**失败响应（HTTP 200 + ok=false）**

```json
{"ok": false, "error": {"code": "revoked", "message": "授权已于 2026-11-20 10:00 被吊销"}}
```

- `code = "revoked"`：客户端会**永久标记吊销**（本地写 `revoked_at`），之后即使
  服务器恢复也不放行（需重新激活）。
- `code = "expired"`：客户端只记录错误，到期判断仍以本地许可证的 `expires_at` 为准。
- 其它错误码：只提示，不影响可用性判断。

> ⚠️ **不要用 HTTP 4xx 表示"授权失效"**，用 200 + `ok=false`。4xx 会被客户端
> 当成"服务器暂时不可用"，只推迟确认而不改变授权状态。4xx 只用于参数错误
> （400/404 等真正的请求错误）。

## 6. 许可证与签名（最关键的一节）

### 6.1 payload 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| license_id | string | 许可证号，唯一。建议 `LIC-yyyymmdd-随机4位` |
| machine_code | string | 绑定机器码。**必须**与请求里的完全一致（大写、带分组横杠） |
| customer | string | 客户名称（客户端界面展示） |
| edition | string | 版本标识，如 `standard` / `pro`。客户端目前不解析，留给将来 |
| issued_at | string | 签发时间，ISO8601 **带时区**（如 `2026-11-13T21:02:53+08:00`） |
| expires_at | string | 到期时间，同上。**客户端只信这个字段**，本地时间超过即 `expired` |
| grace_days | int | 离线宽限天数，默认 7。**以许可证为准**（客户端配置只是兜底） |
| features | string[] | 功能位，预留。目前客户端不校验 |

### 6.2 签名原文的序列化规则（**必须逐字节一致**）

```python
import json
def payload_bytes(payload: dict) -> bytes:
    return json.dumps(payload, ensure_ascii=False, sort_keys=True,
                      separators=(",", ":")).encode("utf-8")
```

三点不能错：

1. **递归键排序**（`sort_keys=True`）；
2. **无空格的紧凑分隔符**（`separators=(",", ":")`）；
3. **中文不转义**（`ensure_ascii=False`）。

其它语言注意：Node 用 `JSON.stringify` 无法直接排序键，需要自己实现递归排序
后再序列化；Java 用 Jackson 时 `ORDER_MAP_ENTRIES_BY_KEYS=true` 且不要
`ESCAPE_NON_ASCII`；Go 的 `encoding/json` 会对 map 键排序（符合要求）但会转义
HTML 字符（`<`, `>`, `&`），需 `SetEscapeHTML(false)`。

**自检方法**：用参考实现签一张证，客户端能激活成功，就说明序列化一致。

### 6.3 签名与验签

```python
# 服务端（私钥只在服务器）
signature = Ed25519_private_key.sign(payload_bytes(payload))
doc = {"key_id": key_id, "payload": payload,
       "signature": base64.b64encode(signature).decode()}
```

```python
# 客户端（内置公钥，见 app/license.py 的 PUBLIC_KEYS）
pub = Ed25519PublicKey.from_public_bytes(base64.b64decode(PUBLIC_KEYS[d["key_id"]]))
pub.verify(base64.b64decode(d["signature"]), payload_bytes(d["payload"]))
```

- `key_id` 用于密钥轮换：客户端内置多把公钥，服务器签发时用当前那一把的 id。
- 客户端遇到不认识的 `key_id` 会给「客户端版本可能过旧」的提示，所以**换密钥
  必须保证旧客户端仍能验旧证**（旧公钥不要从客户端删掉）。

### 6.4 生成密钥对

```bash
cd kefu-system
python tools/gen_license_keys.py --out tools/license_keys --key-id prod-2026
# 打印的 base64 公钥 → 粘贴到 app/license.py 的 PUBLIC_KEYS
```

- **私钥只放服务器**，绝不进客户端安装包、绝不进 git（仓库里的
  `tools/license_keys/dev_private.pem` 是联调用的，正式环境务必换掉）。
- 建议：私钥用 KMS/加密配置文件存储，服务启动时读入内存。

## 7. 错误码表

客户端对部分码有专门的提示文案（`app/api/router_license.py` 的 `_ERROR_HINTS`）。

| code | HTTP | 含义 | 建议提示 |
|---|---|---|---|
| `activation_required` | 400 | 需要激活码 | 请把机器码发给供应商换取激活码 |
| `invalid_code` | 400 | 激活码不存在 | 激活码不正确，请核对 |
| `code_used` | 409 | 激活码已被其它机器使用 | 该激活码已被使用，请联系供应商 |
| `invalid_machine_code` | 400 | 机器码格式不对 | 机器码格式不正确，请重新复制 |
| `not_found` | 404 | 无授权记录 | 没有这台电脑的授权记录 |
| `machine_mismatch` | 409 | 许可证绑定机器码不符 | 许可证与本机不匹配 |
| `revoked` | 200 | 已吊销（用 ok=false） | 授权已被吊销，请联系供应商 |
| `expired` | 200 | 已到期（用 ok=false） | 授权已到期，请续费 |

未定义的码客户端按「请稍后重试或联系供应商」兜底展示，不会崩。

## 8. 数据表设计建议

参考实现用 JSON 文件；正式后台建议用数据库，核心两张表：

```sql
-- 激活码
CREATE TABLE license_code (
  code            VARCHAR(32) PRIMARY KEY,      -- KF-XXXX-XXXX-XXXX-XXXX
  days            INT NOT NULL,                 -- 兑换后的有效天数
  customer        VARCHAR(128) DEFAULT '',
  edition         VARCHAR(32)  DEFAULT 'standard',
  note            VARCHAR(255) DEFAULT '',
  used_machine    VARCHAR(64)  DEFAULT '',      -- 已绑定的机器码，空=未使用
  used_at         DATETIME     NULL,
  created_at      DATETIME     NOT NULL
);

-- 许可证（一台机器一条有效记录）
CREATE TABLE license (
  license_id      VARCHAR(32) PRIMARY KEY,
  machine_code    VARCHAR(64) NOT NULL,
  customer        VARCHAR(128) DEFAULT '',
  edition         VARCHAR(32)  DEFAULT 'standard',
  activation_code VARCHAR(32)  DEFAULT '',
  issued_at       DATETIME     NOT NULL,
  expires_at      DATETIME     NOT NULL,        -- 续期就是改这一列
  grace_days      INT          DEFAULT 7,
  revoked_at      DATETIME     NULL,
  last_seen_at    DATETIME     NULL,
  app_version     VARCHAR(32)  DEFAULT '',
  os              VARCHAR(64)  DEFAULT ''
);
CREATE UNIQUE INDEX uk_license_machine ON license(machine_code);
```

设计要点：

- `machine_code` 唯一索引（一台机器一条记录）——重复激活走"返回原证"的分支。
- 续期只改 `expires_at`，`license_id` 不变（客户本地记录不用重写）。
- 吊销只写 `revoked_at`，不删数据（可追溯、可恢复）。

## 9. 安全与部署要求

1. **必须 HTTPS**。客户端支持 http（联调用），但正式环境走 http 等于把激活码
   和许可证暴露在网络上。
2. **管理接口必须鉴权**。参考实现的 `/admin/*` 无鉴权，只为联调；正式后台
   必须登录 + 权限 + 操作审计（谁给谁延期了多久）。
3. **速率限制**：`/activate` 按机器码/IP 限流（如 10 次/分钟），防激活码爆破。
4. **审计与告警**：同一机器码短时间从多个 IP 确认、同一激活码多次失败，都值得告警
   （整盘 Ghost 到多台机器是这套机制的已知盲区，只能靠服务端策略发现）。
5. **私钥安全**：不进客户端、不进代码仓库、不留备份在可公网访问的机器上。
6. **时间**：所有时间字段**必须带时区**。只写 `2026-11-13T21:02:53`（无时区）
   时客户端按本地时区解释，跨时区客户会提前/延后到期。

## 10. 客户端要改的几处（换到正式后台时）

| 位置 | 改什么 |
|---|---|

| `app/config.py` → `DEFAULT_SETTINGS[license.enabled]` | 保持默认 `"1"`（强制授权）。**不要**改成 `0`——v2 起 `0/false/空` 都不再等于关闭授权 |
| `app/license.py` → `DEV_TOKEN_SHA256` | 测试口令的 SHA256（明文只在内部维护文档，不进程序目录） |
| `app/config.py` → `APP_VERSION` | 发版时同步更新（会随 activate 请求上报） |

### 授权开关（v2：默认强制 + 测试口令）

`license.enabled` 只有两种语义，**判定失败一律按「需要授权」处理（fail-closed）**：

| 取值 | 结果 |
|---|---|
| 等于厂商测试口令（明文）或其 SHA256 指纹 | 测试模式：关闭授权校验，界面红色横幅 |
| `1` / `0` / `false` / `off` / 空 / 其它任意值 | **一律需要授权**（改库不再能绕过） |

优先级：`KEFU_LICENSE_MODE=enforce`（环境变量，强制授权，**无视**测试口令）
> `KEFU_LICENSE_ENABLED` > 数据库 `license.enabled` > `app/config.py` 默认值。

> 注意：环境变量优先级高于数据库，所以**别把 `KEFU_LICENSE_ENABLED` 长期
> 设成测试口令**——那会让 `--license-on` 看起来不生效。切模式统一用下面的命令。

常用命令（在 `kefu-system/` 目录下执行，改完重启生效）：

```bat
python run.py --license-on     :: 切回强制授权（写 license.enabled=1）
python run.py --license-dev    :: 切到测试模式（写口令指纹，内部调试用）
python run.py --license        :: 本次启动强制授权（写环境变量，交付脚本用它）
```

交付客户的启动脚本建议始终带 `--license`：这样即使客户从某处知道了测试口令，
写进数据库也进不了测试模式。

## 12. 常见问题

**Q：客户换电脑了怎么办？**
新机器码不同 → 原有许可证验不过（`invalid`）→ 在管理端给新机器码登记/发新激活码。
旧记录可以留着（不影响）。

**Q：客户重装系统？**
`MachineGuid` 会变 → 机器码变 → 需要重新授权。这是"一机一码"的必然代价，
可在管理端按客户名快速找到并重新发码。

**Q：客户断网了会用不了吗？**
不会。`grace_days`（默认 7 天）内照常可用，界面提示"离线运行中"。

**Q：客户改系统时间想绕过到期？**
本地有时间回拨检测（`clock_rollback`），且真正权威是服务器心跳。别指望客户端
绝对防破解——它的目标是"让正常客户按合同付费"，不是对抗专业破解者。真要更强，
可缩短 `grace_days`、把 `expires_at` 压短（如 30 天，靠心跳自动续）。

**Q：能不能一次授权多台电脑？**
当前是 1 台 1 证。多机授权需要后台支持"许可证绑定多个机器码"——客户端侧
只需把 payload 里的 `machine_code` 改成数组，但**需要改客户端代码**，属于后续版本。

**Q：把 `app/config.py` 里 `license.enabled` 改成 `"1"`，重启后为什么还是开发模式？**

> v2 起 `0/false/空` 不再等于「关闭授权」，这条 FAQ 只剩历史意义——如果现在
> 还看到测试模式，说明库里那行是**口令指纹**，执行 `python run.py --license-on`
> 即可切回。

因为 `DEFAULT_SETTINGS` 只在**建库时**用 `INSERT OR IGNORE` 播种，已有数据库里
那行 `license.enabled` 会一直盖住代码默认值。生效顺序是
**`KEFU_LICENSE_MODE` > 环境变量 `KEFU_LICENSE_ENABLED` > settings 表 > config 默认值**。
切模式最省事的两条命令：

```bat
python run.py --license-on     :: 强制授权（写 1）
python run.py --license-dev    :: 测试模式（写口令指纹）
```

也可以直接改数据库：`UPDATE settings SET value='1' WHERE key='license.enabled'`。

`GET /api/license/status` 的 `enabled_source` 字段会直接告诉你当前开关来自
`env-force` / `env` / `db` / `default` 哪一层，设置页「授权」标签也有同一行提示。

**Q：客户把数据库里的 `license.enabled` 改成 0，会不会就免授权了？**

不会。v2 的判定是「**只有等于测试口令才关闭**」，其余取值一律需要授权。
口令明文不写进程序代码（只存 SHA256），`tools/` 与文档里也没有；即便有人
猜到并写进库，交付脚本用 `--license`（`KEFU_LICENSE_MODE=enforce`）启动时
也会被强制覆盖。测试模式在界面上有红色横幅 + 顶栏「测试模式」红标，
日志每次启动也会打 WARNING，交付件里一眼能看出来。
